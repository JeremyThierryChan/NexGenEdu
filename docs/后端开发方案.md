# 后端开发方案（开发阶段：本机 Node + SQLite，不上 Docker）

> 读者：要开始写真实后端的开发者。部署上线那一套（服务器、HTTPS、备份策略）在本文最后
> 只写「触发条件」，不写具体配置 —— 因为现在还没到那一步，先写下来的是**能立刻开工的最小方案**。

## 0. 一句话

**接口层不动**（`contract.ts` 里那 106 个方法已经是契约），把 `lib/backend/api.ts` 的实现从
localStorage 换成 HTTP 调用，服务端在本机用 **Node + SQLite 单文件**跑起来 —— 页面代码一行不改。

## 1. 为什么开发阶段是「本机 Node + SQLite 单文件」，而不是 Docker

| 考虑 | 结论 |
| --- | --- |
| 开发期 Docker 的唯一好处是「环境一致」 | 这里收益很低：只有一台开发机，且这台机器的约束（`~/.npm` 只读，必须 `npm install --cache ./.npm-cache`）用 Docker 反而更绕 |
| 起服务的速度 | `npm run dev` + 一个 Node 进程，改完就生效；容器要挂卷、重建、看日志多一层 |
| 数据量 | 几个班、一年几百节课、一个管理员 —— SQLite 完全够，且**备份 = 复制一个文件** |
| 迁移到别处 | SQLite 单文件让「换机器」= 搬文件；真要上云/多人并发时再换 Postgres，那一步不需要改接口 |

**什么时候才需要 Docker / Postgres**（触发条件，不是现在做）：

- 多人同时写、需要真正的并发控制与备份策略；
- 需要线上常驻（那就要服务器、HTTPS、进程守护，容器化才开始划算）；
- 数据要给别的系统查（报表、BI），或者要接短信/微信这类外部服务。

## 2. 目标架构（开发阶段）

```
浏览器
  ├─ 宣传网站：仍由 Next.js 静态导出（不变）
  └─ 教务后台页面（app/admin/*）
        ↓ 只调这一层，方法签名与 REST 一致
     lib/backend/api.ts        ← 唯一要改的文件：localStorage → fetch
        ↓ HTTP（本机 http://localhost:4000）
     server/（新增）
        ├─ index.ts            HTTP 服务：路由 → 领域函数 → SQLite
        ├─ db.ts               SQLite 连接（WAL、外键、事务）
        ├─ migrations/         版本化迁移脚本
        └─ data/nexgenedu.db   ← 数据库文件（不进 git）
```

**最大的便宜**：业务规则已经是纯函数，服务端可以**原样搬**，不用重写：

| 模块 | 服务端直接复用 |
| --- | --- |
| `enrollment.ts` / `finance.ts` / `attendance.ts` | 课时与金额的口径（实收 = 收款 − 退款、24 小时请假规则…） |
| `followup.ts` / `stats.ts` | 待跟进阈值、教室利用率分母（上课时间每天 14 小时） |
| `inquiry.ts` | 咨询可行性判定（检查的是一整串日期） |
| `pricing.ts` / `teacher-share.ts` | 报价公式与教师分成（`小时数 × 单价 × (0.4 + (人数−1) × 0.1)`） |
| `courses.ts` / `export.ts` | 课程库校验、导出数据集与格式 |

## 3. 技术选型（开发阶段够用就停）

| 项 | 选择 | 理由 |
| --- | --- | --- |
| 运行时 | Node 22（与 CI 一致） | 已在本机与 Actions 上验证过 |
| HTTP | 原生 `node:http` 或 Express 这类轻框架 | 只有十几个资源路由，不值得引入全家桶 |
| 数据库 | SQLite 单文件 | 零运维、备份=复制文件、迁移=搬文件 |
| SQLite 驱动 | `better-sqlite3`（同步 API）或 Node 22 内置的 `node:sqlite` | 同步 API 让「一个请求 = 一个事务」写起来最直白；**选哪个在开工第一步用一次 spike 定下来**（内置模块的成熟度与 API 稳定性需按你当时的 Node 版本确认） |
| 迁移 | 自己的 SQL 迁移器（见第 4 节） | 项目已有版本化迁移的教训与纪律，直接沿用；不引入 ORM 迁移框架 |
| 认证 | 服务端会话（HttpOnly Cookie） | 现在的假登录只是门不是锁，见 `docs/后台API约定.md` 的迁移第 5 步 |
| 校验 | 服务端自己复核 12 项（`SERVER_MUST_VALIDATE`） | 前端校验只是体验，不是保证 |

**明确不做**（开发阶段）：Docker、ORM 全家桶、微服务、消息队列、多租户、Redis 缓存 —— 都不解决当前问题。

## 4. 数据库与迁移（这里最需要纪律）

### 4.1 表结构

照 `lib/backend/types.ts` 建表（它已经是数据契约）：`students` / `teachers` / `classrooms` /
`lessons` / `lesson_records` / `homework_records` / `assessments` / `transactions` / `payments` /
`logs` / `inquiries` / `courses`，外加 `pricing`（单行配置，可存 JSON 列）。

两个刻意的选择：

- **嵌套结构先按 JSON 列存**（`students.enrollments`、`students.profile`、教室 `availability`、
  报价配置）：它们要么是「键值对字段表」要么是「整体读写的小结构」，拆表收益低。
  等真要按课时流水做跨学生统计时，再把 `enrollments` 独立成表。
- **课时与金额留痕不删**：`transactions` / `payments` 只追加，撤销写反向记录 ——
  与现在的口径一致（见 PROJECT.md 的不变式）。

### 4.2 迁移纪律（每一条都对应开发中踩过的坑）

1. `schema_version` 表 + **按版本升序**逐级执行（曾经把分支写反，导致数据停在中间版本、
   被当成坏数据重新灌种子）；
2. **迁移前自动备份**数据库文件（现在的「导入」功能就是三道保险：结构校验 → 自动备份 → 迁移）；
3. 迁移失败**中止并保留原文件**，不要「尽力而为地跑一半」；
4. 版本号只有一个来源（现在是 `lib/backend/version.ts` 的 `CURRENT_VERSION`，当前 **v12**），
   服务端与前端必须认同一个版本号，否则导出/导入会对不上；
5. **不要用「先改数据再比较版本」**的写法（就地修改后比较永远相等，导致迁移被跳过）。

## 5. 动手顺序（每一步都能单独验收）

| 步骤 | 做什么 | 验收 |
| --- | --- | --- |
| 1 | 建 `server/` 骨架：SQLite 连接、迁移器、`GET /health` | `curl localhost:4000/health` 通；迁移脚本能重复执行（幂等） |
| 2 | 实现**只读**接口：`students.list` / `lessons.list` / `teachers.list` / `classrooms.list` / `courses.list` / `today` | 用「数据与备份」页导出的 JSON 灌进 SQLite，页面显示与现在一致 |
| 3 | 数据搬迁：把导出的 JSON 灌入 SQLite（一次性脚本） | 条数与页面上的一致（导出页会显示各表条数） |
| 4 | 实现写接口，先做最关键的十几个：报课 / 续费 / 退课 / 收款 / 排课 / 标记已上 / 请假补课 | 课时与金额不变式成立（复用现有断言） |
| 5 | 前端切换：`api.ts` 内部换成 `fetch`，页面不动 | 页面零改动跑通；开发期用环境变量指向本机服务（如 `NEXT_PUBLIC_API_BASE`），跨端口时开 CORS 或用 Next 的 rewrites 代理成同源 |
| 6 | 认证换成服务端会话 | 未登录时接口 401；前端删除「演示登录」说明 |
| 7 | 把自检改成**跑两遍**：一遍打内存存储、一遍打 HTTP 接口 | 同一套断言两种后端都通过 —— 这是「换后端没改口径」最硬的证据 |

## 6. 备份与恢复（开发阶段就要有，别等到上线）

- 数据库文件不进 git（加进 `.gitignore`），备份目录 `server/backups/`；
- 备份方式：SQLite 的在线备份（`VACUUM INTO '备份文件'`）或直接复制文件（服务停止时）；
- **每天一次自动备份 + 保留最近 N 份**；开发期手动也行，但**恢复必须演练一次** ——
  没演练过的备份不算备份；
- 与现有能力衔接：「数据与备份」页导出的 JSON 仍是**跨系统**的搬运方式（换数据库、换机器都用它）。

## 7. 上线阶段（等触发条件满足再展开）

到那时再决定：自有 VPS + Docker Compose（app + Caddy 反代 + Postgres），或托管平台。
无论哪种，下面三件事都要先成立（它们与用不用 Docker 无关）：

1. 数据写在卷/宿主目录，容器随时可删；
2. 迁移脚本带版本、启动时自动执行、执行前自动备份；
3. 每天自动备份，并且**至少演练过一次恢复**。

另外提醒一个架构事实：前端仍部署在 GitHub Pages（免费静态托管），后端在别处。
要么开 CORS，要么把前端也放到同一台机器上用反向代理做成同域（更省事，我倾向前者只在开发期用）。
