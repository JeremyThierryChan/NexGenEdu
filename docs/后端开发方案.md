# 后端开发方案（开发阶段：本机 Node + SQLite，不上 Docker）

> 读者：要开始写真实后端的开发者。部署上线那一套（服务器、HTTPS、备份策略）在本文最后
> 只写「触发条件」，不写具体配置 —— 因为现在还没到那一步，先写下来的是**能立刻开工的最小方案**。

## 0. 一句话

**接口层不动**（`contract.ts` 里那 106 个方法已经是契约），把 `lib/backend/api.ts` 的实现从
localStorage 换成 HTTP 调用，服务端在本机用 **Node + SQLite 单文件**跑起来 —— 页面代码一行不改。

## 1. 为什么开发阶段是「本机 Node + SQLite 单文件」，而不是 Docker

| 考虑 | 结论 |
| --- | --- |
| 开发期 Docker 的唯一好处是「环境一致」 | 这里收益很低：只有一台开发机，且这台机器的约束（`~/.npm` 只读，必须 `npm install --cache ./.npm-cache`）用 Docker 反而更绕 |
| 起服务的速度 | `npm run dev` + 一个 Node 进程，改完就生效；容器要挂卷、重建、看日志多一层 |
| 数据量 | 几个班、一年几百节课、一个管理员 —— SQLite 完全够，且**备份 = 复制一个文件** |
| 迁移到别处 | SQLite 单文件让「换机器」= 搬文件；真要上云/多人并发时再换 Postgres，那一步不需要改接口 |

**什么时候才需要 Docker / Postgres**（触发条件，不是现在做）：

- 多人同时写、需要真正的并发控制与备份策略；
- 需要线上常驻（那就要服务器、HTTPS、进程守护，容器化才开始划算）；
- 数据要给别的系统查（报表、BI），或者要接短信/微信这类外部服务。

## 2. 目标架构（开发阶段）

```
浏览器
  ├─ 宣传网站：仍由 Next.js 静态导出（不变）
  └─ 教务后台页面（app/admin/*）
        ↓ 只调这一层，方法签名与 REST 一致
     lib/backend/api.ts        ← 唯一要改的文件：localStorage → fetch
        ↓ HTTP（本机 http://localhost:4000）
     server/（新增）
        ├─ index.ts            HTTP 服务：路由 → 领域函数 → SQLite
        ├─ db.ts               SQLite 连接（WAL、外键、事务）
        ├─ migrations/         版本化迁移脚本
        └─ data/nexgenedu.db   ← 数据库文件（不进 git）
```

> **架构已于路线 B 落地（提交 `1f05c90`）**：服务端不再逐个用 SQL 重写方法，而是
> 给 `api.ts` 换一个 **SQLite 支持的 `KeyValueStore`**（表 `kv(key, value)` 存一份 JSON 快照），
> 再用 `POST /api/call { method, args }` 把 **106 个方法**按 `api` 的真实形状暴露出去。
> 因此服务端跑的就是浏览器里那份 `api.ts`，**业务口径一行都没重写**。
> 我在这一轮之前写的那些 SQL 路由（`students`/`lessons`/`payments`… 表）**不是当前的数据通路**，
> 保留下来作为「将来要迁到 SQL」的参考实现与对照。为什么这么选、代价是什么见 §5.3。

**最大的便宜**：业务规则已经是纯函数，服务端可以**原样搬**，不用重写：

| 模块 | 服务端直接复用 |
| --- | --- |
| `enrollment.ts` / `finance.ts` / `attendance.ts` | 课时与金额的口径（实收 = 收款 − 退款、24 小时请假规则…） |
| `followup.ts` / `stats.ts` | 待跟进阈值、教室利用率分母（上课时间每天 14 小时） |
| `inquiry.ts` | 咨询可行性判定（检查的是一整串日期） |
| `pricing.ts` / `teacher-share.ts` | 报价公式与教师分成（`小时数 × 单价 × (0.4 + (人数−1) × 0.1)`） |
| `courses.ts` / `export.ts` | 课程库校验、导出数据集与格式 |

## 3. 技术选型（开发阶段够用就停）

| 项 | 选择 | 理由 |
| --- | --- | --- |
| 运行时 | Node 22（与 CI 一致） | 已在本机与 Actions 上验证过 |
| HTTP | 原生 `node:http` 或 Express 这类轻框架 | 只有十几个资源路由，不值得引入全家桶 |
| 数据库 | SQLite 单文件 | 零运维、备份=复制文件、迁移=搬文件 |
| SQLite 驱动 | **`better-sqlite3`（已定）** | 同步 API 让「一个请求 = 一个事务」写起来最直白（异步驱动要处处 `await`，事务边界容易写错）；生态成熟、`VACUUM INTO` 备份与 WAL 都有现成写法。代价是原生模块，**需要在 `npm install --cache ./.npm-cache` 下验证一次安装与加载**（见 §9） |
| 迁移 | 自己的 SQL 迁移器（见第 4 节） | 项目已有版本化迁移的教训与纪律，直接沿用；不引入 ORM 迁移框架 |
| 认证 | 服务端会话（HttpOnly Cookie） | 现在的假登录只是门不是锁，见 `docs/后台API约定.md` 的迁移第 5 步 |
| 校验 | 服务端自己复核 12 项（`SERVER_MUST_VALIDATE`） | 前端校验只是体验，不是保证 |

**明确不做**（开发阶段）：Docker、ORM 全家桶、微服务、消息队列、多租户、Redis 缓存 —— 都不解决当前问题。

## 4. 数据库与迁移（这里最需要纪律）

### 4.1 表结构

照 `lib/backend/types.ts` 建表（它已经是数据契约）：`students` / `teachers` / `classrooms` /
`lessons` / `lesson_records` / `homework_records` / `assessments` / `transactions` / `payments` /
`logs` / `inquiries` / `courses`，外加 `pricing`（单行配置，可存 JSON 列）。

两个刻意的选择：

- **嵌套结构先按 JSON 列存**（`students.enrollments`、`students.profile`、教室 `availability`、
  报价配置）：它们要么是「键值对字段表」要么是「整体读写的小结构」，拆表收益低。
  等真要按课时流水做跨学生统计时，再把 `enrollments` 独立成表。
- **课时与金额留痕不删**：`transactions` / `payments` 只追加，撤销写反向记录 ——
  与现在的口径一致（见 PROJECT.md 的不变式）。

### 4.2 迁移纪律（每一条都对应开发中踩过的坑）

1. `schema_version` 表 + **按版本升序**逐级执行（曾经把分支写反，导致数据停在中间版本、
   被当成坏数据重新灌种子）；
2. **迁移前自动备份**数据库文件（现在的「导入」功能就是三道保险：结构校验 → 自动备份 → 迁移）；
3. 迁移失败**中止并保留原文件**，不要「尽力而为地跑一半」；
4. 版本号只有一个来源（现在是 `lib/backend/version.ts` 的 `CURRENT_VERSION`，当前 **v12**），
   服务端与前端必须认同一个版本号，否则导出/导入会对不上；
5. **不要用「先改数据再比较版本」**的写法（就地修改后比较永远相等，导致迁移被跳过）。

## 5. 动手顺序（每一步都能单独验收）

| 步骤 | 做什么 | 验收 |
| --- | --- | --- |
| 1 | 建 `server/` 骨架：SQLite 连接、迁移器、`GET /health` | `curl localhost:4000/health` 通；迁移脚本能重复执行（幂等） |
| 2 | 实现**只读**接口：`students.list` / `lessons.list` / `teachers.list` / `classrooms.list` / `courses.list` / `today` | 用「数据与备份」页导出的 JSON 灌进 SQLite，页面显示与现在一致 |
| 3 | 数据搬迁：把导出的 JSON 灌入 SQLite（一次性脚本） | 条数与页面上的一致（导出页会显示各表条数） |
| 4 | 实现写接口，先做最关键的十几个：报课 / 续费 / 退课 / 收款 / 排课 / 标记已上 / 请假补课 | 课时与金额不变式成立（复用现有断言） |
| 5 | 前端切换：`api.ts` 内部换成 `fetch`，页面不动 | 页面零改动跑通；开发期用环境变量指向本机服务（如 `NEXT_PUBLIC_API_BASE`），跨端口时开 CORS 或用 Next 的 rewrites 代理成同源 |
| 6 | 认证换成服务端会话 | 未登录时接口 401；前端删除「演示登录」说明 |
| 7 | 把自检改成**跑两遍**：一遍打内存存储、一遍打 HTTP 接口 | 同一套断言两种后端都通过 —— 这是「换后端没改口径」最硬的证据 |

### 5.1 第 5 步（前端整体切换）的准备工作 —— 精确缺口清单

> **路线 B 落地后，这份清单被大幅简化**：不再需要逐个在服务端实现 66 个方法，
> `/api/call` 一次覆盖全部 106 个（跑的是同一份 `api.ts`）。
> 剩下真正要做的只有三件事：
>
> 1. **换掉 `seed.ts`**：新库（空存储）一启动会**自动灌入示例数据** ——
>    实测空库调用 `students.list` 直接返回 8 条示例学生。机构已经清空过库、
>    要求删掉示例数据，所以服务端起步必须是**空库**，`api.reset()` 也要一并处理；
> 2. **校准各写方法的入参**：通过 RPC 调用时参数形状必须与 `types.ts` 的入参一致。
>    实测里我把报课的字段名猜成 `totalLessons`，结果写进去是 `null` ——
>    **报课、退费、排课、标记已上、咨询等写方法都要照类型定义逐个验一遍**，不能靠猜；
> 3. **第 5 步切换**：把 `lib/backend/api.ts` 的实现换成对 `/api/call` 的 `fetch`，
>    仍然**只改这一个文件**，页面一行不动。
>
> 下面是路线 A（SQL 原生实现）的清单，保留作为将来迁移时的对照。

**界面实际调用 66 个方法**（契约共 106 个，其余是页面没用到的）。切换前端之前，
这 66 个必须都有服务端实现，否则页面会点到"还没有这个接口"。

### 5.2 剩下三块「必须搬、不能重写」的逻辑（下一轮的起点）

服务端还缺的部分里，有四块**不能凭印象在服务端重写**，必须把既有实现抽成
纯函数模块、前后端共用（这与报价公式、课时记账是同一条原则）：

| 要搬的 | 现在在哪 | 为什么不能重写 |
| --- | --- | --- |
| **排课冲突判定** `findConflicts` | `lib/backend/api.ts` 的 lessons 组 | 五类问题（教师/教室/学生冲突、教室时段、容量、教师科目）各有边界：相邻不算冲突、已取消不占时间、编辑自己不算冲突 —— 少一条就会放行一个错误排课 |
| **课时扣减与对账** `reconcileCharge` + `recordPayment` | 同文件顶部 | 直接决定钱与课时：「实收 = 收款 − 退款」「已用课时 = 有效上课流水」，写错就是账对不上 |
| **补课与待补课** `createMakeup` / `pendingMakeups` | lessons 组 | 与请假规则、24 小时口径耦合（临时缺课 + 补课 = 扣 2 节） |
| **咨询判定与采用** `evaluate` / `accept` | inquiries 组 | `accept` 落库前要**再复核一次**；这是"当场答应家长"的依据 |

**搬的办法（下一轮按这个做）**：

1. 在 `lib/backend/` 新建纯函数模块（例如 `conflicts.ts`、`charges.ts`），把上面这些逻辑
   **原样**从 `api.ts` 移过去，`api.ts` 改成调用新模块 —— 这一步不改行为，跑 `npm run check`
   应当**一条断言都不变**（这是"搬运没改口径"的证据）；
2. 服务端直接 import 这些纯函数（loader 已经能解析 `@/` 别名）；
3. 补上服务端对应的路由，并用独立测试库跑端到端：冲突放行/拦截的边界用例、
   扣课时幂等、缺课+补课=2 节、退费金额、咨询判定能排/不能排。

#### 5.2.2 课时流水的真实语义（**我早期手写的 SQL 实现与它不一致**）

通过 `/api/call` 验证时发现的差异，值得单记一条：

| | 真实实现（`api.ts`） | 我早期手写的 SQL 路由 |
| --- | --- | --- |
| `students.enroll` 报课时写什么 | 报课记录里的 **history**（`kind: "报课"`）+ 一条**收款**流水；**不写课时流水** | 我额外写了一条 `kind: "报课"` 的课时流水 —— **多写了** |
| `transactions`（课时流水）记什么 | 记**上课扣减**（`kind: "上课"`）与 `调整` / `退课` 等变动 | 同左（但多出了报课那一条） |
| 剩余课时的算法 | `remainingOf = totalLessons − usedLessons`（两个都是记录上的字段），
报课与续费的课时靠 `totalLessons` 累加体现，**不靠流水汇总** | 同左 |

也就是说：`TRANSACTION_KINDS = ["报课", "续费", "上课", "调整", "退课"]` 里的
「报课 / 续费」指的是**报课记录里的 history 条目**，不是课时流水。我早期把两者混在一起写，
导致"课时流水合计"这个数字在两套实现下不一致 —— 而这正是**路线 B 要消除的那类风险**：
口径写两遍，两套结果不同，最后谁都说不清算的是哪一套。

结论：SQL 那批路由**只作参考**，不接进数据通路（§2 已注明）；要迁到 SQL 时，
这张表就是必须照抄的口径。这条差异也是"不在服务端重写业务逻辑"这一决定的最好注脚。

### 5.3 一个重要发现：纯函数吃的是「内存 Database」，不是 SQL 行

搬运 `reconcileCharge` / `recordPayment` 时发现：这些纯函数的签名是
`(db: Database, ...)` —— 它们操作的是**内存里的数组结构**（`db.students`、`db.payments`…），
而我服务端现在是**SQL 表**。所以「服务端直接调用这些纯函数」这条路**不通**，
除非写一层适配：把整库读进内存 → 调用纯函数 → 把变化写回 SQL（读全库、写全库）。

三条可选路线：

| 路线 | 做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| **A. SQL 原生实现**（我这几轮在做的） | 在服务端用 SQL 重写每个方法的逻辑 | 查询/索引/并发都正常，是"真后端"的样子 | **等于把口径写第二遍**（课时、金额、冲突判定…），两边迟早分叉 |
| **B. 服务端 KeyValueStore + 统一分发**（推荐先走） | `api.ts` 本来就与存储解耦（`KeyValueStore`：浏览器里是 localStorage、Node 里是内存）。给它加一个**服务端实现**（存进 SQLite 的单表或 JSON 文件），再用一个通用分发路由把 106 个方法暴露成 HTTP | **零重写**：所有口径天然只有一份（就是现有 `api.ts`）；第 5 步切换会变得很小；与文档既定的「换后端只替换 `api.ts` 的实现」完全一致 | 不是关系型用法：没有按行查询、没有并发控制、数据量大了要改（本机构目前是 KB 级、单管理员） |
| **C. A 为长期、B 为过渡** | 先用 B 把系统跑起来、机构真正开始用，等数据量与并发真的成为问题时，再逐表迁到 A（接口形状不变，页面永远不动） | 风险最低、见效最快 | 需要一次"从 blob 到表"的迁移（数据量小，成本低） |

**已实施（提交 `1f05c90`）**：`server/kv-store.mts`（SQLite 支持的 KeyValueStore）+
`/api/call` 通用分发。实测通过：建学生 / 读列表 / 日志同套写入 / 未知方法明确报错 /
未实现路径 404 / **重启服务后数据仍在**。同时实测出三件事（都写进了 §5.1）：
空库会自动播种示例数据；重启后数据确实落盘（我一开始把断言写错）；报课入参字段名我猜错了。

**建议：B →（必要时）C**。理由是它把"口径只有一份"这条最重要的事变成了结构性保证，
而不是靠人记住"改这边也要改那边"。A 路线最容易出的事故恰恰是我们最怕的：
SQL 里写一套、纯函数里写一套，某天对账对不上却查不出是谁算的。

如果采用 B，下一步是：
1. 给服务端写一个 `KeyValueStore` 实现（表 `kv(key TEXT PRIMARY KEY, value TEXT)` 存一份 JSON 快照，
   写入时整份写回 —— 与 localStorage 的语义一致，因此 `api.ts` 不需要任何改动）；
2. 加一个通用分发路由（例如 `POST /api/call { method: "students.list", args: [] }`），
   按 `api` 的真实形状逐级查表调用；未登录/未知方法返回明确错误；
3. 把已有的 SQL 路由（我这轮写的那些）**暂时保留**，作为"以后迁到 A"的参考实现与对照；
4. 第 5 步切换时把 `api.ts` 的实现换成对 `/api/call` 的 fetch —— 仍然只改这一个文件。

### 5.4 使用形态已定：**单用户、本地使用**（暂不上服务器）

机构确认：暂时只有一个人用，不部署到公网。因此：

| 项 | 结论 |
| --- | --- |
| 后端部署 | **暂不做**（不上 VPS、不做 HTTPS、不做反向代理），§7 的上线阶段推迟 |
| 日常怎么用 | 本机同时跑两个进程：`npm run server`（后端 + SQLite）+ `npm run dev`（前端） |
| 数据在哪 | `server/data/nexgenedu.db`（SQLite 单文件），备份 = 复制文件或 `VACUUM INTO` |
| 并发/权限 | 单用户不需要（真鉴权也只是"门"）；`SERVER_MUST_VALIDATE` 那 12 项仍然保留，等上服务器时用 |

**一个必须处理的副作用**：后台页面切到 `fetch` 之后，**线上（GitHub Pages）那份后台会连不到后端**。
处理办法（切换时实现）：

- 用 `NEXT_PUBLIC_API_BASE` 环境变量切换数据源：
  - **本机**（`.env.local` 里设置）→ 走 `fetch`，数据进 SQLite —— 这是真正的使用环境；
  - **线上构建**（不设置）→ 保持现在的 localStorage 行为，并在后台顶部显示一条明确提示：
    「这是线上演示环境：数据只存在这台电脑的浏览器里；正式使用请在本机运行 `npm run server` + `npm run dev`」。
- 这样做的理由：线上站点是给家长看的（静态站，不需要后端），**不该因为后台切换而整个打不开**；
  而两套环境的差别（本机=真实数据 / 线上=演示）用一条横幅讲清楚，不让人误会数据在哪。
- 等哪天真要多人/远程使用，再把 `NEXT_PUBLIC_API_BASE` 指向那台服务器即可 —— **页面代码不用改**。

## 6. 备份与恢复（开发阶段就要有，别等到上线）

- 数据库文件不进 git（加进 `.gitignore`），备份目录 `server/backups/`；
- 备份方式：SQLite 的在线备份（`VACUUM INTO '备份文件'`）或直接复制文件（服务停止时）；
- **每天一次自动备份 + 保留最近 N 份**；开发期手动也行，但**恢复必须演练一次** ——
  没演练过的备份不算备份；
- 与现有能力衔接：「数据与备份」页导出的 JSON 仍是**跨系统**的搬运方式（换数据库、换机器都用它）。

## 7. 上线阶段（等触发条件满足再展开）

到那时再决定：自有 VPS + Docker Compose（app + Caddy 反代 + Postgres），或托管平台。
无论哪种，下面三件事都要先成立（它们与用不用 Docker 无关）：

1. 数据写在卷/宿主目录，容器随时可删；
2. 迁移脚本带版本、启动时自动执行、执行前自动备份；
3. 每天自动备份，并且**至少演练过一次恢复**。

另外提醒一个架构事实：前端仍部署在 GitHub Pages（免费静态托管），后端在别处。
要么开 CORS，要么把前端也放到同一台机器上用反向代理做成同域（更省事，我倾向前者只在开发期用）。

## 9. 数据库选型：SQLite + better-sqlite3（已定）

**选定：SQLite 单文件 + `better-sqlite3` 驱动。**

| 项 | 定下来的内容 |
| --- | --- |
| 数据库 | SQLite（单文件 `server/data/nexgenedu.db`，不进 git） |
| 驱动 | `better-sqlite3`（同步 API） |
| 连接参数 | `journal_mode = WAL`（读写不互相阻塞）、`foreign_keys = ON`、`busy_timeout = 5000`（写冲突时等一会儿而不是立刻报错） |
| 事务 | 一个 HTTP 请求 = 一个事务；`better-sqlite3` 的 `db.transaction(fn)` 包住「改数字 + 写流水 + 写日志」这类多表动作 |
| 备份 | `VACUUM INTO 'server/backups/nexgenedu-YYYY-MM-DD.db'`（在线备份，不用停服务） |
| 迁移记录 | `schema_version` 表 + `server/migrations/*.sql` 按版本升序执行 |

为什么是 `better-sqlite3` 而不是 Node 内置的 `node:sqlite`：后者是实验性 API，会随 Node 版本变动，
而我们的迁移器与备份逻辑要靠它长期稳定；前者的同步事务写法与本项目「一个动作一个事务」的
口径天然契合。**代价**：它是原生模块，安装要编译。因此开工第一步就要验证：

```bash
npm install --cache ./.npm-cache better-sqlite3
node -e "const D=require('better-sqlite3');const db=new D(':memory:');db.exec('create table t(a)');console.log('better-sqlite3 OK', db.prepare('select 1 as x').get())"
```

装不上（编译工具链缺失）时的退路，按顺序：① 用 Node 22 的 `node:sqlite` 顶上（API 不同，
但我们的迁移器与业务函数不受影响，只换 `db.ts` 一层）；② 再看 `sql.js`（WASM，无需编译，
但整库在内存里、写入要自己落盘 —— 只适合开发期应急）。

## 10. 数据迁移：网站内容与后台数据都要进库

现在的数据在**两个地方**，迁进数据库时要分开对待 —— 这一点必须先讲清楚，因为它们的「真源」
归属不同，选错了以后每改一次文案都要重新导入。

| 数据 | 现在在哪 | 体量 | 迁进库之后谁是「真源」 |
| --- | --- | --- | --- |
| 后台业务数据（学生 / 教师 / 教室 / 排课 / 报课 / 收款 / 课时流水 / 咨询 / 操作日志 / 课程库 / 报价配置） | 管理员那台浏览器的 localStorage | 小 | **数据库**（唯一真源，本来就是这么设计的） |
| 网站内容（首页文案、课程栏目卡片、教师介绍、FAQ、案例、时间安排、特色课程、报价数据） | `data/site/*.md`（构建期打包进静态站） | 约 10 个文件 | **见下面的分岔** |

### 10.1 网站内容的真源归属（**已定：方案 B —— 内容文件是真源，数据库存镜像**）

**采用 B**：`data/site/*.md` 继续是公开文案的**唯一真源**；服务端把它解析后写入
数据库的 `site_content` 表，作为**只读镜像**。镜像的用途是「后台能统一查询、能基于它做校验」，
**不是**让后台去改它 —— 改文案仍然走：改 Markdown → `npm run sync-content` → `npm run check` → 提交发布。

这么定的理由：保住 GitHub Pages 的免费静态托管与现在的发布流程（内容是低频改动，
为它把整站变成动态服务并不划算），同时让数据在库里就位、将来想切换时不用重新搬一遍。

| | 真源 | 谁改它 | 一致性靠什么 |
| --- | --- | --- | --- |
| `data/site/*.md` | ✅ 公开文案的真源 | 运营改文件（或后台导出的 Markdown 粘回去） | —— |
| `site_content` 表（镜像） | ❌ 只读副本 | 只有同步脚本会写；后台界面不给编辑入口 | 同步幂等（内容哈希判据）+ `npm run check` |

**将来若要切成「数据库做真源」（方案 A）**，触发条件是「机构要自己在后台在线改文案、改完立即生效」。
那时的改动很有限：把同步方向反过来（数据库当源、Markdown 变成导出产物），
业务表与 106 个接口都不用动。**这一刻不要提前做** —— 做了就失去静态托管这个便宜。

**镜像必须做对的三件事**（否则它会变成一份没人维护的假数据）：

1. **单向**：只允许 `md → db`，不允许任何界面写 `site_content`（不给入口，不是不给按钮）；
2. **幂等 + 可校验**：按内容文件哈希判断是否需要重写，重复同步不产生重复行；
   同步后打印「页面数 / 卡片数 / FAQ 条数」这类可核对的数字（与 `npm run check` 的口径一致）；
3. **过期要能看出来**：镜像表记下「来自哪个文件、同步时间、内容哈希」，
   后台读它时能显示「镜像同步于 X，可能与线上不一致」——宁可让人看到它旧了，也别假装它是对的。

### 10.2 迁移步骤（两条来源都覆盖）

1. **后台数据**：在旧站点（浏览器里）打开「数据与备份」→「导出全部数据（JSON）」→
   在服务端跑导入脚本把 JSON 灌进 SQLite → **核对每条表的条数**（导出页会显示各表条数，
   导入脚本也要打印一份对比）→ 导入前自动备份数据库文件（与现在的「导入」功能同一套三道保险）。
2. **网站内容（镜像）**：写一个 `server/import-content.ts`，用现有的数据层（`lib/data/*`，
   已有解析器）把 `data/site/*.md` 解析后写入 `site_content` 表（按 `页面/分组/节/条目` 存行，
   保留原始 Markdown 以便将来导出）。**不要重新写一套 Markdown 解析** —— 解析器是本项目
   最容易出错的地方，已经有自检覆盖它。按 §10.1 的三条要求做成**单向、幂等、可看出过期**的镜像。
3. **保持一致**：内容同步与后台数据导入都要**幂等**（重复跑不产生重复行）；
   同步用内容文件的哈希做判据，没变就跳过。
4. **验收**：① 后台各页显示的条数与导出 JSON 一致；② 课程库的课程名与网站课程卡片一致；
   ③ 报价配置与 `data/site/pricing.md` 一致；④ **同一套自检跑两遍**（内存存储 + HTTP 接口）
   都通过。第 ④ 条是「迁移没丢东西也没改口径」最硬的证据。

### 7.1 上线前必须清掉的「伪后端痕迹」清单

这些文字在开发阶段是**必要的诚实提示**，上线后如果留着就变成了假话（或者误导）：

| 位置 | 现在写的 | 上线时怎么处理 |
