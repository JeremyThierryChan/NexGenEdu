> 读者：**要维护这个后端、或将来要把它改大的人**。
> 本文原来是一份"准备开工的方案"，现在这一步**已经做完了**，所以它更主要的用处是：
> 说清楚**为什么这么做**（尤其 §5.3 为什么不让服务端重写业务逻辑）、
> **验收靠什么**（§5.6 / §5.7 / §6 / §5.5 各自的命令）、以及**哪些坑踩过了**。

## 0. 一句话（✅ **已经做完**，本文现在是"怎么做的 + 为什么"的记录）

**接口层不动**（`contract.ts` 里那 106 个方法就是契约），服务端在本机用
**Node + SQLite 单文件**跑起来，页面代码一行不改。

实际落地的方式与最初设想略有不同，值得先说清楚：**没有**把 `api.ts` 改写成 fetch 版，
而是在 `api.ts` 里加了一层**远端代理**（`lib/backend/remote.ts`：遍历本地实现的方法结构，
逐个生成对 `POST /api/call` 的调用），由 `NEXT_PUBLIC_API_BASE` 决定导出哪一份。
好处是"少写一个方法、参数传错一个字段"这类**静默错误**从结构上不可能发生 ——
方法名、参数个数、返回类型全都与本地实现同源。代价与取舍见 §5.3。

> 现在的状态：迁移六步全部走完（含服务端会话认证 §5.6 与"两种后端跑同一套自检" §5.7），
> 备份与恢复演练也做了（§6）。**还没做**的是网站内容进库做只读镜像（§10.2 第 2 条）。

## 1. 为什么开发阶段是「本机 Node + SQLite 单文件」，而不是 Docker

| 考虑 | 结论 |
| --- | --- |
| 开发期 Docker 的唯一好处是「环境一致」 | 这里收益很低：只有一台开发机，且这台机器的约束（`~/.npm` 只读，必须 `npm install --cache ./.npm-cache`）用 Docker 反而更绕 |
| 起服务的速度 | `npm run dev` + 一个 Node 进程，改完就生效；容器要挂卷、重建、看日志多一层 |
| 数据量 | 几个班、一年几百节课、一个管理员 —— SQLite 完全够，且**备份 = 复制一个文件** |
| 迁移到别处 | SQLite 单文件让「换机器」= 搬文件；真要上云/多人并发时再换 Postgres，那一步不需要改接口 |

**什么时候才需要 Docker / Postgres**（触发条件，不是现在做）：

- 多人同时写、需要真正的并发控制与备份策略；
- 需要线上常驻（那就要服务器、HTTPS、进程守护，容器化才开始划算）；
- 数据要给别的系统查（报表、BI），或者要接短信/微信这类外部服务。

## 2. 目标架构（开发阶段）

实际的样子（括号里是文件）：

```
浏览器
  ├─ 宣传网站：仍由 Next.js 静态导出（不变，不含任何后端依赖）
  └─ 教务后台页面（app/admin/*）—— 页面代码一行没改
        ↓ 只调 api 这一层
     lib/backend/api.ts
        ├─ 本地实现（localApi）：localStorage / 内存
        └─ 远端代理：api.ts 按 NEXT_PUBLIC_API_BASE 决定导出哪一个
              ↓ HTTP（本机 http://127.0.0.1:4000，带 Bearer 令牌）
     server/（新增）
        ├─ index.mts        HTTP 服务：/api/login /api/logout /api/session
        │                   /api/status /api/call + 鉴权闸门 + 备份调度
        ├─ auth.mts         口令与会话（口令不进数据库）
        ├─ backup.mts       每天备份 + 保留份数（backup-cli.mts 是命令行入口）
        ├─ kv-store.mts     用 SQLite 实现的 KeyValueStore（kv 表存一份 JSON 快照）
        ├─ db.mts           SQLite 连接（WAL、外键、事务）+ 备份原语与命名规则
        ├─ migrate.mts      版本化迁移（迁移前自动备份）
        ├─ migrations/      迁移脚本（001_init.sql、002_records.sql）
        └─ data/nexgenedu.db  ← 数据库文件（不进 git）
```

**关键点**：服务端 `import` 的就是浏览器里那份 `lib/backend/api.ts`，只是把它的存储换成了
SQLite —— 所以课时、金额、冲突判定、报价这些口径**物理上只有一份实现**，
不存在"SQL 里一套、纯函数里一套"的分叉风险。

> **架构已于路线 B 落地（提交 `1f05c90`）**：服务端不再逐个用 SQL 重写方法，而是
> 给 `api.ts` 换一个 **SQLite 支持的 `KeyValueStore`**（表 `kv(key, value)` 存一份 JSON 快照），
> 再用 `POST /api/call { method, args }` 把 **106 个方法**按 `api` 的真实形状暴露出去。
> 因此服务端跑的就是浏览器里那份 `api.ts`，**业务口径一行都没重写**。
> 我在这一轮之前写的那些 SQL 路由（`students`/`lessons`/`payments`… 表）**不是当前的数据通路**，
> 保留下来作为「将来要迁到 SQL」的参考实现与对照。为什么这么选、代价是什么见 §5.3。

**最大的便宜**：业务规则已经是纯函数，服务端可以**原样搬**，不用重写：

| 模块 | 服务端直接复用 |
| --- | --- |
| `enrollment.ts` / `finance.ts` / `attendance.ts` | 课时与金额的口径（实收 = 收款 − 退款、24 小时请假规则…） |
| `followup.ts` / `stats.ts` | 待跟进阈值、教室利用率分母（上课时间每天 14 小时） |
| `inquiry.ts` | 咨询可行性判定（检查的是一整串日期） |
| `pricing.ts` / `teacher-share.ts` | 报价公式与教师分成（`小时数 × 单价 × (0.4 + (人数−1) × 0.1)`） |
| `courses.ts` / `export.ts` | 课程库校验、导出数据集与格式 |

## 3. 技术选型（开发阶段够用就停）

| 项 | 选择 | 理由 |
| --- | --- | --- |
| 运行时 | Node ≥ 22.6（与 CI 一致） | 已在本机与 Actions 上验证过。**22.6 是硬要求**：`--experimental-strip-types` 从 22.6 才有，而本项目的门禁脚本都靠它直接跑 `.mts` |
| HTTP | 原生 `node:http` 或 Express 这类轻框架 | 只有十几个资源路由，不值得引入全家桶 |
| 数据库 | SQLite 单文件 | 零运维、备份=复制文件、迁移=搬文件 |
| SQLite 驱动 | **`better-sqlite3`（已定）** | 同步 API 让「一个请求 = 一个事务」写起来最直白（异步驱动要处处 `await`，事务边界容易写错）；生态成熟、`VACUUM INTO` 备份与 WAL 都有现成写法。代价是原生模块，**需要在 `npm install --cache ./.npm-cache` 下验证一次安装与加载**（见 §9） |
| 迁移 | 自己的 SQL 迁移器（见第 4 节） | 项目已有版本化迁移的教训与纪律，直接沿用；不引入 ORM 迁移框架 |
| 认证 | 服务端会话（**已实现**：口令在服务端、令牌在内存、Bearer 头） | 见 §5.6。当时计划用 HttpOnly Cookie，实际用 Bearer 令牌：静态导出的前端不带服务端运行时，Cookie 的 SameSite/域配置反而更绕；上公网时应改回 Cookie + HTTPS（那时令牌不该暴露给 JS） |
| 校验 | 服务端自己复核 12 项（`SERVER_MUST_VALIDATE`） | 前端校验只是体验，不是保证 |

**明确不做**（开发阶段）：Docker、ORM 全家桶、微服务、消息队列、多租户、Redis 缓存 —— 都不解决当前问题。

## 4. 数据库与迁移（这里最需要纪律）

### 4.1 表结构

照 `lib/backend/types.ts` 建表（它已经是数据契约）：`students` / `teachers` / `classrooms` /
`lessons` / `lesson_records` / `homework_records` / `assessments` / `transactions` / `payments` /
`logs` / `inquiries` / `courses`，外加 `pricing`（单行配置，可存 JSON 列）。

两个刻意的选择：

- **嵌套结构先按 JSON 列存**（`students.enrollments`、`students.profile`、教室 `availability`、
  报价配置）：它们要么是「键值对字段表」要么是「整体读写的小结构」，拆表收益低。
  等真要按课时流水做跨学生统计时，再把 `enrollments` 独立成表。
- **课时与金额留痕不删**：`transactions` / `payments` 只追加，撤销写反向记录 ——
  与现在的口径一致（见 PROJECT.md 的不变式）。

### 4.2 迁移纪律（每一条都对应开发中踩过的坑）

1. `schema_version` 表 + **按版本升序**逐级执行（曾经把分支写反，导致数据停在中间版本、
   被当成坏数据重新灌种子）；
2. **迁移前自动备份**数据库文件（「导入」功能就是三道保险：结构校验 → 自动备份 → 迁移）。
   迁移快照的文件名**刻意不匹配每日备份的命名规则**（`nexgenedu-migrate-<时间戳>.db`）：
   于是它既不参与"今天已备份"的判定、也不会被保留份数清掉 ——
   否则一次结构变更就可能把当天的每日备份"顶掉"。
   另外它必须尊重 `NEXGENEDU_NO_BACKUP` 与 `NEXGENEDU_BACKUP_DIR`：
   早期这两条都没接上，导致**每起一个临时库服务都往真实备份目录丢一个空库备份**，
   而那些文件会满足"今天已备份"的判定，让**真实库当天一份备份都没有**（见 §6.1）；
3. 迁移失败**中止并保留原文件**，不要「尽力而为地跑一半」；
4. 版本号只有一个来源（现在是 `lib/backend/version.ts` 的 `CURRENT_VERSION`，当前 **v13**），
   服务端与前端必须认同一个版本号，否则导出/导入会对不上；
5. **不要用「先改数据再比较版本」**的写法（就地修改后比较永远相等，导致迁移被跳过）。

### 5.2 「必须搬、不能重写」的四块逻辑（✅ **路线 B 之后不需要搬了**）

> **结论先说**：这一节当时的前提是"服务端要用 SQL 重写这些逻辑"，因此必须先抽成
> 纯函数模块才能两端共用。**路线 B 之后这个前提消失了** —— 服务端跑的就是同一份
> `api.ts`，这些逻辑天然只有一份，一行都不用搬。
>
> 保留这一节是因为它记录了一个**判断**：哪四块逻辑"重写一遍就会出事"。
> 将来真要迁到 SQL（§5.3 路线 C）时，这份清单就是**必须先抽成纯函数、不许凭印象重写**的名单。
> 其中冲突判定、课时记账、报价公式**当时已经**抽成了独立纯函数模块
> （`conflicts` / `charges` / `pricing` 等，见 §5.2）

这四块**不能凭印象在服务端重写**，必须把既有实现抽成纯函数模块、前后端共用
（这与报价公式、课时记账是同一条原则）：

| 要搬的 | 现在在哪 | 为什么不能重写 |
| --- | --- | --- |
| **排课冲突判定** `findConflicts` | `lib/backend/api.ts` 的 lessons 组 | 五类问题（教师/教室/学生冲突、教室时段、容量、教师科目）各有边界：相邻不算冲突、已取消不占时间、编辑自己不算冲突 —— 少一条就会放行一个错误排课 |
| **课时扣减与对账** `reconcileCharge` + `recordPayment` | 同文件顶部 | 直接决定钱与课时：「实收 = 收款 − 退款」「已用课时 = 有效上课流水」，写错就是账对不上 |
| **补课与待补课** `createMakeup` / `pendingMakeups` | lessons 组 | 与请假规则、24 小时口径耦合（临时缺课 + 补课 = 扣 2 节） |
| **咨询判定与采用** `evaluate` / `accept` | inquiries 组 | `accept` 落库前要**再复核一次**；这是"当场答应家长"的依据 |

**搬的办法（路线 C 真要迁 SQL 时按这个做）**：

1. 在 `lib/backend/` 新建纯函数模块（例如 `conflicts.ts`、`charges.ts`），把上面这些逻辑
   **原样**从 `api.ts` 移过去，`api.ts` 改成调用新模块 —— 这一步不改行为，跑 `npm run check`
   应当**一条断言都不变**（这是"搬运没改口径"的证据）；
2. 服务端直接 import 这些纯函数（loader 已经能解析 `@/` 别名）；
3. 补上服务端对应的路由，并用独立测试库跑端到端：冲突放行/拦截的边界用例、
   扣课时幂等、缺课+补课=2 节、退费金额、咨询判定能排/不能排。

#### 5.2.2 课时流水的语义（**早期两套实现不一致，现已统一**）

通过 `/api/call` 验证时发现的差异，值得单记一条 —— 因为**结论后来被翻过来了**：

| | 当时的真实实现（`api.ts`） | 我早期手写的 SQL 路由 | 现在（已统一） |
| --- | --- | --- | --- |
| `students.enroll` 报课时写什么 | 报课记录里的 **history**（`kind: "报课"`）+ 一条**收款**流水；**不写课时流水** | 写了一条 `kind: "报课"` 的课时流水 | **两边都写**：history + 一条 `报课` 课时流水 |
| `transactions`（课时流水）记什么 | 只记**上课扣减**（`kind: "上课"`） | 记报课 + 上课 | 报课 / 续费 / 调整 / 退课 / 上课 **全记** |
| 剩余课时的算法 | `remainingOf = totalLessons − usedLessons`（记录上的字段），不靠流水汇总 | 同左 | 同左（流水与字段的关系由不变式约束，见下） |

当时我按「SQL 路由多写了」把差异判给了 SQL 那一边，理由是——账面实现摆在那里，
不要拿手写实现去改它。**这个判断是错的**：机构刚报完 20 节，打开「课时流水」
看到的却是空的（账本里只有「上课」），只能怀疑数据没存上；「先看流水再问钱」是
最常用的对账路径，空账本等于没有账本。演示数据（`seed.ts`）本来就是
「history 与流水两边都写」，新录入的没有理由不同规矩。

现在的口径（`docs/后台API约定.md` §6.3 有完整版）：

```
该报课下「有效流水」之和 === 总课时 − 已用课时
其中「上课」流水之和 === −已用课时（撤销的不计）
```

调整记的是**实际生效**的节数（课时不会被调成负数），退课记 `0` 节（只改状态、
不减总课时，与 v4→v5 迁移的折算规则一致）。

结论保持不变的另一半：SQL 那批路由**只作参考**，不接进数据通路（§2 已注明）；
要迁到 SQL 时，这张表就是必须照抄的口径。这条差异也是"不在服务端重写业务逻辑"
这一决定的最好注脚 —— 只是当年照抄的是**错的那一边**，
真正发现问题靠的是「自检里那条不变式其实一直是空转的」（见 `scripts/check.mts`
里 `ledgerConsistent` 的注释）。

### 5.3 一个重要发现：纯函数吃的是「内存 Database」，不是 SQL 行

搬运 `reconcileCharge` / `recordPayment` 时发现：这些纯函数的签名是
`(db: Database, ...)` —— 它们操作的是**内存里的数组结构**（`db.students`、`db.payments`…），
而我服务端现在是**SQL 表**。所以「服务端直接调用这些纯函数」这条路**不通**，
除非写一层适配：把整库读进内存 → 调用纯函数 → 把变化写回 SQL（读全库、写全库）。

三条可选路线：

| 路线 | 做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| **A. SQL 原生实现**（我这几轮在做的） | 在服务端用 SQL 重写每个方法的逻辑 | 查询/索引/并发都正常，是"真后端"的样子 | **等于把口径写第二遍**（课时、金额、冲突判定…），两边迟早分叉 |
| **B. 服务端 KeyValueStore + 统一分发**（推荐先走） | `api.ts` 本来就与存储解耦（`KeyValueStore`：浏览器里是 localStorage、Node 里是内存）。给它加一个**服务端实现**（存进 SQLite 的单表或 JSON 文件），再用一个通用分发路由把 106 个方法暴露成 HTTP | **零重写**：所有口径天然只有一份（就是现有 `api.ts`）；第 5 步切换会变得很小；与文档既定的「换后端只替换 `api.ts` 的实现」完全一致 | 不是关系型用法：没有按行查询、没有并发控制、数据量大了要改（本机构目前是 KB 级、单管理员） |
| **C. A 为长期、B 为过渡** | 先用 B 把系统跑起来、机构真正开始用，等数据量与并发真的成为问题时，再逐表迁到 A（接口形状不变，页面永远不动） | 风险最低、见效最快 | 需要一次"从 blob 到表"的迁移（数据量小，成本低） |

**已实施（提交 `1f05c90`，并一直用到今天）**：`server/kv-store.mts`（SQLite 支持的
KeyValueStore）+ `/api/call` 通用分发。实测通过：建学生 / 读列表 / 日志同套写入 /
未知方法明确报错 / 未实现路径 404 / **重启服务后数据仍在**。同时实测出三件事（都写进了 §5.1）：
空库会自动播种示例数据；重启后数据确实落盘（我一开始把断言写错）；报课入参字段名我猜错了。

**这条路选对了，而且后来拿到了硬证据**：`npm run check:both`（§5.7）把同一套断言
（`npm run check` 里那 700+ 条）对**内存后端**与**真实 HTTP 后端**各跑一遍，两边都通过 ——
这就是"口径只有一份"的证明。
如果走的是路线 A（SQL 重写一遍），这一步会变成"两套实现各跑各的、差异只能靠人比"。

**结论：B →（必要时）C**，理由不变 —— 它把"口径只有一份"变成了**结构性保证**，
而不是靠人记住"改这边也要改那边"。A 路线最容易出的事故恰恰是我们最怕的：
SQL 里写一套、纯函数里写一套，某天对账对不上却查不出是谁算的。

**B 之后又做了什么、下一步是什么**：

1. ✅ 服务端 `KeyValueStore` 实现（表 `kv(key TEXT PRIMARY KEY, value TEXT)` 存一份 JSON 快照，
   写入时整份写回 —— 与 localStorage 的语义一致，因此 `api.ts` 不需要任何改动）；
2. ✅ 通用分发路由 `POST /api/call { method, args }`，按 `api` 的真实形状逐级查表调用；
   未知方法返回明确错误。**未登录返回 401**（第 6 步加的，见 §5.6）；
3. ✅ 已有的 SQL 路由**保留下来了**，作为"以后迁到 A"的参考实现与对照 ——
   它们现在也要求登录（只锁新门、忘了旧窗等于没锁）；
4. ✅ 前端切换：加了一层远端代理（`lib/backend/remote.ts`），`api.ts` 按环境变量导出对应实现 ——
   仍然只改这一个文件，页面一行不动。

**还没到 C**：触发条件是"数据量或并发真的成问题"。目前是 KB 级、单管理员，
所以先不迁；真迁的时候，§5.1 那两张路线 A 快照表与 §5.2 的四块逻辑清单就是现成的对照。

### 5.4 使用形态已定：**单用户、本地使用**（暂不上服务器）

机构确认：暂时只有一个人用，不部署到公网。因此：

| 项 | 结论 |
| --- | --- |
| 后端部署 | **暂不做**（不上 VPS、不做 HTTPS、不做反向代理），§7 的上线阶段推迟 |
| 日常怎么用 | 本机同时跑两个进程：`npm run server`（后端 + SQLite）+ `npm run dev`（前端）；登录用后端启动时打印的口令 |
| 数据在哪 | `server/data/nexgenedu.db`（SQLite 单文件）；**每天自动备份**到 `server/backups/`（保留 90 份），恢复演练见 §6.2 |
| 并发/权限 | 单用户不需要并发控制与权限区分；`SERVER_MUST_VALIDATE` 那 12 项仍然保留，等上服务器时用 |
| 监听地址 | 后端默认只绑 `127.0.0.1`（`NEXGENEDU_HOST` 可覆盖）—— 本机使用的系统没必要监听所有网卡 |

**一个必须处理的副作用（✅ 已处理）**：后台页面切到 `fetch` 之后，**线上（GitHub Pages）那份后台连不到后端**。
当时的计划是"线上保持 localStorage 行为 + 一条横幅"，**实际做法更彻底一点**：

- 用 `NEXT_PUBLIC_API_BASE` 环境变量切换数据源：
  - **本机**（`.env.local` 里设置）→ 走后端，数据进 SQLite —— 这是真正的使用环境；
  - **线上构建**（不设置）→ 后台**不假装能用**：登录页直接说明"没有后端可连、无法登录"，
    进入 `/admin` 会看到"后台需要本机后端"并给出两条命令；提示条也照实说"线上静态站不保存数据"。
- 为什么**没有**让线上继续用 localStorage：那样"能登进去、能录数据"，
  但录的数据在别人自己的浏览器里，换台电脑就看不到 —— 对一个已经把数据搬到服务端的系统，
  这是最容易让人误判的一种状态（以为录进去了）。**说了不能用的代价，远小于让人以为能用。**
- 宣传站本身不受任何影响：它是纯静态导出，给家长看的部分一行都没变。
- 等哪天真要多人/远程使用，再把 `NEXT_PUBLIC_API_BASE` 指向那台服务器即可 —— **页面代码不用改**。

### 5.5 逐页验收结果与「可以放心用 + 已知限制」

**验收方式**：`npm run accept`（`scripts/accept-run.mts` 起一个临时库的真实后端，

不是"打开看看"），全程不碰真实数据。

> 没指就**直接退出**。因为 `createKeyValueStore()` 在 Node 里会静默退化成内存存储 ——
> 忘了设环境变量时，它会安静地测一遍伪后端、还照样打印「43/43 通过」。
> **一份假证据比不跑更糟**：它让人以为真实后端验过了。

**结果：43/43 全部通过**（课程库 5、教室 2、教师 2、学生 4、收费 3、课程安排 9、日历 1、

**验收抓到的真 bug（已修）**：远端代理用 JSON 传参，`Date` 被序列化成字符串，
于是 `finance(new Date())` 报 `anchor.getFullYear is not a function` ——
凡是要传日期的方法（日历、统计、收费、按日取课）都会中招。
修法：代理把 `Date` 显式标记成 `{ __date: ISO }`，服务端还原（**不能**"看到像日期的字符串就转"，
`startedAt`/`startsAt` 这些参数本来就是字符串，乱转一样错）。

**可以放心用的部分**：

- 课时与金额的不变式（实收 = 收款 − 退款、已用课时 = 有效上课流水、超扣报错、标记已上幂等）；

### 5.6 第 6 步：服务端会话认证（✅ 已实现）

**为什么必须做**：数据搬进服务端之后，"口令写在前端"就不再可接受了 —— 仓库是公开的，
公开的口令等于没有口令，而它现在守的是钱、课时与家长联系方式。

| 项 | 定下来的内容 |
| --- | --- |
| 口令存哪 | 服务端。`NEXGENEDU_ADMIN_PASSWORD` 优先；否则**首次启动随机生成**并写入 `server/data/admin-credential.json`（0600），启动日志打印一次 |
| 为什么不进数据库 | 数据库会被备份/导出/恢复。"恢复三个月前的备份"会把口令一起回退成三个月前的 —— 那种故障很难联想到，而且正好发生在手忙脚乱恢复数据的时候 |
| 校验 | `scrypt` + 随机盐（Node 内置 crypto，不引第三方）；比较用 `timingSafeEqual`；失败**不区分**"账号不存在"与"口令不对" |
| 令牌 | 32 字节随机、放**服务端内存**、闲置 12 小时过期（每次使用续期）。重启即失效 —— 单用户本机使用，重新登录一次不麻烦，而持久化要带来一整套过期与回收逻辑 |
| 前端拿什么 | 只拿令牌（`lib/auth/token.ts`）。口令从不经过前端 |
| 鉴权范围 | `/api/` 下除 `/api/login`、`/api/logout`、`/api/session` 外**一律要登录**（一处闸门，见下） |
| 监听地址 | 默认 `127.0.0.1`（`NEXGENEDU_HOST` 可改）。原来监听所有网卡，同一个 WiFi 下谁都能连 —— 对"本机单用户"的系统是不必要的暴露 |
| 探活 | `/health` 公开但只回服务名+库文件名；细节（库路径、迁移、各表条数、备份状态）挪到 `/api/status`，要登录 |

**鉴权要做成结构性的，不能逐个接口加**：第一版我按分支加，结果 `/api/call`、报价、
通用增删改都挡上了，**唯独漏了读接口**（未登录直接 200 把学生数据交出去）。
漏法很隐蔽（"我明明加了鉴权"）。所以改成：**只要在 `/api/` 下，默认就是关门状态**，
新加接口不需要谁记得加一行。

**顺带修掉的一处静默错误**：操作日志的操作人原来由前端调 `api.setOperator(name)` 告诉服务端，
而它是**同步方法**、经远端代理会静默变成 Promise —— 于是操作日志里操作人一直是默认值。
现在操作人由服务端按**会话**设置（kv 那套日志用 `api.setOperator`，
服务端自己写 SQL 的那套用 `currentOperator`，少设一个就会在一条路上退回默认值）。

**验收**：`npm run check:auth`（起临时后端，用真实 HTTP 当外人打）：
未登录 401、401 不带数据、探活不泄露表结构、错口令与错账号同一句话、伪造令牌 401、
退出后令牌立刻作废、操作人来自会话、老 REST 接口同样受保护。

### 5.7 第 7 步：同一套自检对两种后端各跑一遍（✅ 已实现）

`npm run check:both`：先跑内存后端，再起一个**临时库**的真实服务端把**同一份**
`check.mts` 跑第二遍，两边都必须 0 失败。这是"换后端没改口径"最硬的证据 ——
断言一条没为远端改，只是把后端换成了真实服务端。

**它真的抓到了东西（都是"不报错、只答错"的类型）**：

1. `api` 上的**同步方法**经远端代理会变成 Promise：`hasBackup()` 让数据与备份页
   **永远显示"有备份可恢复"**；`setOperator()` 让操作日志的操作人**永远是默认值**。
   修法不只是把两个方法改成 async，还在 `api.ts` 底部加了**类型级断言** ——
   api 上再出现同步方法会直接编译失败（这道闸加上的当场就点名了 `setOperator`）；
2. **老库升级那 4 段是"假通过"**：它们把老数据写进**浏览器存储**再读回来，
   走服务端时读的是 SQLite，于是断言全绿却什么都没验。改成走 `api.importDatabase()`
   （真实用户升级数据的路径，两种后端都跑得到），覆盖反而变高；
3. **自检依赖"首次访问灌示例学生"**：服务端是空库起步，于是对不上。改为夹具经
   **导入接口**进入当前后端，两种后端拿到同一份夹具，断言才有可比性。

**顺带立的一条护栏**：`check:both` 会对比真实备份目录在跑前跑后的文件集合 ——
临时服务动了它就直接失败（这个坑见 §6.1）。

### 5.8 容量与设备要求（**实测数字**）

这一节回答两个常被问到的问题：**"这台机器要什么配置？"** 与 **"能撑多少人？"**
数字来自 `npm run bench:capacity`（合成数据、跑在临时库上、不碰真实数据），
你可以隔一段时间自己重跑一遍，看增长曲线。

#### 先分清两种"人数"

| 谁 | 靠什么扛 | 能有多少 |
| --- | --- | --- |
| **家长 / 访客**（宣传网站） | GitHub Pages 的 CDN，静态文件，**不经过你的机器** | 基本无上限（GitHub 的软限制是每月 100GB 流量、站点 1GB；一页约 100KB） |
| **用后台的人**（教务/负责人） | 自己这台电脑上的 Node 进程 | **同一时刻 1 个写入者** —— 这是设计约束，不是机器不够 |

**第二种"人数"的瓶颈是并发，不是性能。** 存储是快照式的（§5.3 路线 B）：
整库一份 JSON，谁最后写谁覆盖。两个人同时改同一份数据会互相盖掉，
所以文档里一直写"单用户"。要给多人同时用，需要的是**并发控制**（版本号 / 事务 / 锁）
或迁到按行存储（路线 C）—— 换一台更贵的机器**不解决**这个问题。

#### 数据量怎么涨（决定成本的那个变量）

成本随**整库行数**增长，而不是随"你改的那一行"增长 —— 因为每次写入都会把整库重新
序列化并落盘。一所辅导机构的数据量大致是：**学生数 × 每人每年 50–100 节课**。

| 学生 | 排课（约一年） | JSON 快照 | 库文件 | 序列化+落盘 | 冷读（含解析） | 热读 | 写入一次 | 进程内存 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 20 | 1,000 | 405 KB | 405 KB | 1 ms | 3 ms | ~0 ms | 2 ms | 122 MB |
| 100 | 5,000 | 1.6 MB | 1.6 MB | 3 ms | 10 ms | ~0 ms | 6 ms | 146 MB |
| 300 | 15,000 | 4.8 MB | 4.8 MB | 17 ms | 30 ms | 2 ms | 18 ms | 233 MB |
| 800 | 40,000 | 12.6 MB | 12.6 MB | 45 ms | 76 ms | 3 ms | 47 ms | 377 MB |

（"写入一次"= 走完整业务方法的一次写入，含校验、记账、写日志 —— 也就是用户按下按钮真正感受到的那一下。
本机后端与浏览器在同一台机器上，网络耗时可以忽略。）

> **数字怎么读**：这是**数量级与趋势**，不是基准测试。同一台机器上同时跑别的重活时，
> 实测能差 2–4 倍（写这份文档时就复现过：800 名学生那档从 47ms 变成 186ms）。
> 结论"设备要求很低"因此是有余量的判断 —— 真要卡到人感知（约 100ms 以上）还得再涨一个数量级。

#### 结论：设备要求其实很低

- **机器**：任何能跑 Node ≥ 22.6 与浏览器的电脑。**十年前的笔记本（4–8GB 内存）完全够** ——
  上表最重的一档（800 名学生 / 4 万节课 ≈ 几年的数据）单次写入也只有 ~50ms，人的感知阈值是 ~100ms。
- **内存**：Node 基线约 40–60MB + 快照的 2–3 倍（整库会在进程里驻留一份）。
  100 名学生时实测 146MB；2GB 内存的机器也不紧张。
- **磁盘**：库文件 + **备份**。备份是整份复制，所以**磁盘占用 ≈ 快照大小 × 保留份数**：
  100 名学生（1.6MB）× 90 份 ≈ 150MB；800 名学生（12.6MB）× 90 份 ≈ 1.1GB。
  这是唯一需要留意的地方 —— 数据大了要么调小保留份数（`NEXGENEDU_BACKUP_KEEP`），要么接受这个占用。
- **SSD 还是机械盘**：都可以。但每次写入要落 0.4–13MB，机械盘上会更"卡顿"一点，SSD 更舒服。

#### 什么时候该迁到按行存储（路线 C）

**触发条件不是"人多了"，而是下面任意一条**：

1. **写入开始有感知**（连续超过 ~100–200ms）：按上表的线性趋势，大约在**上千名学生**
   或**五六年历史数据**（几万节课）之后；
2. **要多人同时用**（真正的原因通常是这个）；
3. 要按行查询/出报表，不想每次把整库读进内存。

到那时接口形状不变、页面不动，只换存储层（§5.3 路线 C）。

#### 一条测量教训：瓶颈曾经是一个 `sleep`

第一次量的时候，所有操作的耗时都"恰好"在 120ms 附近 —— 看起来像设备不行。
真实原因在 `lib/backend/api.ts`：`LATENCY_MS = 120` 的**模拟网络延迟**
（为让浏览器里的加载态可见而加），它在服务端也照样生效：**每个请求白等 120ms**，
而真实计算量在百人规模上只有几毫秒。`npm run check` 也因此从 38 秒降到 0.9 秒
（38 秒里约 37 秒在 sleep）。

现在那道延迟**只在浏览器里生效**（`typeof window !== "undefined"`）—— 它本来就只为
"让人看见加载态"存在，而服务端与测试里没有加载态要看。**教训**：性能结论必须来自
"把人工延迟排除掉"的测量，否则你优化的是错觉。

## 6. 备份与恢复（✅ 已实现，见 §6.1 / §6.2）

- 数据库文件不进 git（加进 `.gitignore`），备份目录 `server/backups/`；
- 备份方式：SQLite 的在线备份（`VACUUM INTO '备份文件'`），**不用停服务**；
- **每天一次自动备份 + 保留最近 N 份**（默认 90 份）；**恢复已演练过**；
- 与现有能力衔接：「数据与备份」页导出的 JSON 仍是**跨系统**的搬运方式（换数据库、换机器都用它）。

### 6.1 自动备份怎么做的（`server/backup.mts`）

| 项 | 定下来的内容 |
| --- | --- |
| 触发 | **启动时补齐**（昨天关机、今天开机第一件事就是备上）+ **每小时检查一次**（长期开着的机器也能跨过零点） |
| 频次 | 每天**一份**；判定口径只有一处实现（`backupIfNotToday`），写在两处迟早分叉成"启动按 24 小时算、定时器按自然日算" |
| 保留 | 默认 90 份（`NEXGENEDU_BACKUP_KEEP`），**只删命名规则内的文件**，删除逐条打印 |
| 命名 | `nexgenedu-YYYY-MM-DD-HH-mm-ss.db`（**本地时间**）。排序与"哪份最新"一律以**文件名**为准，不看 mtime —— mtime 会被复制/移动/恢复操作改写 |
| 手动 | `npm run server:backup`（动数据前备一份、服务没开也能备、可接 cron/launchd） |
| 可见 | `/api/status` 里报目录与最近一份；备份是"出事那天才想起来检查"的东西，平时也要看得见 |
| 隔离 | `NEXGENEDU_NO_BACKUP=1` 关掉（自检/验收的临时库用）；`NEXGENEDU_BACKUP_DIR` 换目录（演练/测试用） |

**踩过的坑（都会造成"以为备了"）**：迁移器的"执行前自动备份"写死了真实目录，
于是每起一个临时库服务都往 `server/backups/` 丢一个空库备份 —— 真正的危险不是脏，
而是那些文件会满足"今天已备份"的判定，**让真实库当天一份备份都没有**。
现在 `check:both` 会对比真实备份目录在跑前跑后的文件集合，被动过就失败。

### 6.2 恢复演练（`npm run drill:restore`）

**没演练过的备份不算备份。** 最容易出的事故不是"忘了备"，而是"以为备了"：
文件不存在 / 是空的 / 是旧库的 / 出事时没人知道怎么恢复。演练把四件事一次证伪：

1. 起临时库 → 写可识别数据（1 学生 / 20 课时 / 3600 元 / 扣 1 节）；
2. 备份，并**先验备份文件本身**（能打开、且内容就是备份那一刻的数据，含课时账本）；
3. 停服务、**删掉数据库文件**（连同 -wal/-shm，模拟"文件没了"）；
4. 只靠备份文件恢复 → 重启 → 核对条数、金额、课时账本**完全一致**。

演练同时覆盖备份策略本身：保留份数生效、被清理的是最旧的、目录里非备份文件一根手指都不碰、
同一天不重复备。

## 9. 数据库选型：SQLite + better-sqlite3（✅ 已落地并按此实现）

**选定：SQLite 单文件 + `better-sqlite3` 驱动。**

| 项 | 定下来的内容 |
| --- | --- |
| 数据库 | SQLite（单文件 `server/data/nexgenedu.db`，不进 git） |
| 驱动 | `better-sqlite3`（同步 API） |
| 连接参数 | `journal_mode = WAL`（读写不互相阻塞）、`foreign_keys = ON`、`busy_timeout = 5000`（写冲突时等一会儿而不是立刻报错） |
| 事务 | 一个 HTTP 请求 = 一个事务；`better-sqlite3` 的 `db.transaction(fn)` 包住「改数字 + 写流水 + 写日志」这类多表动作 |
| 备份 | `VACUUM INTO 'server/backups/nexgenedu-YYYY-MM-DD.db'`（在线备份，不用停服务） |
| 迁移记录 | `schema_version` 表 + `server/migrations/*.sql` 按版本升序执行 |

为什么是 `better-sqlite3` 而不是 Node 内置的 `node:sqlite`：后者是实验性 API，会随 Node 版本变动，
而我们的迁移器与备份逻辑要靠它长期稳定；前者的同步事务写法与本项目「一个动作一个事务」的
口径天然契合。**代价**：它是原生模块，安装要编译。因此开工第一步就要验证：

```bash
npm install --cache ./.npm-cache better-sqlite3
node -e "const D=require('better-sqlite3');const db=new D(':memory:');db.exec('create table t(a)');console.log('better-sqlite3 OK', db.prepare('select 1 as x').get())"
```

装不上（编译工具链缺失）时的退路，按顺序：① 用 Node 22 的 `node:sqlite` 顶上（API 不同，
但我们的迁移器与业务函数不受影响，只换 `db.ts` 一层）；② 再看 `sql.js`（WASM，无需编译，
但整库在内存里、写入要自己落盘 —— 只适合开发期应急）。

## 10. 数据迁移：网站内容与后台数据都要进库

现在的数据在**两个地方**，迁进数据库时要分开对待 —— 这一点必须先讲清楚，因为它们的「真源」
归属不同，选错了以后每改一次文案都要重新导入。

| 数据 | 现在在哪 | 体量 | 迁进库之后谁是「真源」 |
| --- | --- | --- | --- |
| 后台业务数据（学生 / 教师 / 教室 / 排课 / 报课 / 收款 / 课时流水 / 咨询 / 操作日志 / 课程库 / 报价配置） | 管理员那台浏览器的 localStorage | 小 | **数据库**（唯一真源，本来就是这么设计的） |
| 网站内容（首页文案、课程栏目卡片、教师介绍、FAQ、案例、时间安排、特色课程、报价数据） | `data/site/*.md`（构建期打包进静态站） | 约 10 个文件 | **见下面的分岔** |

### 10.1 网站内容的真源归属（**已定：方案 B —— 内容文件是真源，数据库存镜像**）

**采用 B**：`data/site/*.md` 继续是公开文案的**唯一真源**；服务端把它解析后写入
数据库的 `site_content` 表，作为**只读镜像**。镜像的用途是「后台能统一查询、能基于它做校验」，
**不是**让后台去改它 —— 改文案仍然走：改 Markdown → `npm run sync-content` → `npm run check` → 提交发布。

这么定的理由：保住 GitHub Pages 的免费静态托管与现在的发布流程（内容是低频改动，
为它把整站变成动态服务并不划算），同时让数据在库里就位、将来想切换时不用重新搬一遍。

| | 真源 | 谁改它 | 一致性靠什么 |
| --- | --- | --- | --- |
| `data/site/*.md` | ✅ 公开文案的真源 | 运营改文件（或后台导出的 Markdown 粘回去） | —— |
| `site_content` 表（镜像） | ❌ 只读副本 | 只有同步脚本会写；后台界面不给编辑入口 | 同步幂等（内容哈希判据）+ `npm run check` |

**将来若要切成「数据库做真源」（方案 A）**，触发条件是「机构要自己在后台在线改文案、改完立即生效」。
那时的改动很有限：把同步方向反过来（数据库当源、Markdown 变成导出产物），
业务表与 106 个接口都不用动。**这一刻不要提前做** —— 做了就失去静态托管这个便宜。

**镜像必须做对的三件事**（否则它会变成一份没人维护的假数据）：

1. **单向**：只允许 `md → db`，不允许任何界面写 `site_content`（不给入口，不是不给按钮）；
2. **幂等 + 可校验**：按内容文件哈希判断是否需要重写，重复同步不产生重复行；
   同步后打印「页面数 / 卡片数 / FAQ 条数」这类可核对的数字（与 `npm run check` 的口径一致）；
3. **过期要能看出来**：镜像表记下「来自哪个文件、同步时间、内容哈希」，
   后台读它时能显示「镜像同步于 X，可能与线上不一致」——宁可让人看到它旧了，也别假装它是对的。

### 10.2 迁移步骤（两条来源都覆盖）

| 步骤 | 状态 |
| --- | --- |
| 1. **后台数据**（浏览器 → SQLite） | ✅ 做过：`npm run server:import`（导入前自动 `VACUUM INTO` 备份）。机构后来把库清空、从零开始录，所以现在库里业务数据是空的 |
| 2. **网站内容（只读镜像）** | ❌ **未做**：`site_content` 表已建好（迁移 `001_init.sql`），但**没有同步脚本**、库里 0 行 |
| 3. **幂等** | ✅ 导入是幂等的（同一份 JSON 重复导入不产生重复行）；镜像那侧还没做，因此"用内容文件哈希做判据"也还没落地 |
| 4. **验收** | ✅ ① ② ③ 由 `npm run accept`（对后台各页面真实读写）与 `check.mts` 里"同步来源 = 网站内容"这类断言覆盖；④ 由 `npm run check:both` 覆盖 |

原来的步骤说明保留在下面，作为**做第 2 条时的要求**：

1. **后台数据**：在旧站点打开「数据与备份」→「导出全部数据（JSON）」→
   在服务端跑导入脚本把 JSON 灌进 SQLite → **核对每条表的条数**（导出页会显示各表条数，
   导入脚本也要打印一份对比）→ 导入前自动备份数据库文件（与「导入」功能同一套三道保险）。
2. **网站内容（镜像）**：写一个 `server/import-content.ts`，用现有的数据层（`lib/data/*`，
   已有解析器）把 `data/site/*.md` 解析后写入 `site_content` 表（按 `页面/分组/节/条目` 存行，
   保留原始 Markdown 以便将来导出）。**不要重新写一套 Markdown 解析** —— 解析器是本项目
   最容易出错的地方，已经有自检覆盖它。按 §10.1 的三条要求做成**单向、幂等、可看出过期**的镜像
   （单向：不给任何界面写它的入口；幂等 + 可校验：按内容哈希判断、同步后打印可核对的数字；
   过期要能看出来：记下来源文件、同步时间、内容哈希）。
3. **保持一致**：内容同步与后台数据导入都要**幂等**（重复跑不产生重复行）；
   同步用内容文件的哈希做判据，没变就跳过。
4. **验收**：① 后台各页显示的条数与导出 JSON 一致；② 课程库的课程名与网站课程卡片一致；
   ③ 报价配置与 `data/site/pricing.md` 一致；④ **同一套自检跑两遍**（内存存储 + HTTP 接口）
   都通过。第 ④ 条是「迁移没丢东西也没改口径」最硬的证据。

> **第 2 条要不要做**：触发条件是"机构想在后台在线改文案、或想基于网站内容做校验"。
> 现在没这个需求，所以先不做 —— 见 §10.1「这一刻不要提前做」的理由（保住静态托管的便宜）。

### 7.1 上线前必须清掉的「伪后端痕迹」清单（✅ **已全部清掉**）

这些文字在开发阶段是**必要的诚实提示**，接上真实后端后如果留着就变成了假话（或者误导）。
下表是清单与**处理结果**（保留清单本身，是因为"哪些话什么时候会变成假话"这件事值得记住）：

| 位置 | 当时写的 | 处理结果 |
| --- | --- | --- |
| `components/admin/DataNotice.tsx` | 「数据保存在这台电脑的浏览器里…」 | ✅ 改成按模式说真话：连后端时「数据在服务端数据库、后端每天自动备份」；没连后端时说清「线上静态站、不保存数据、无法登录」 |
| `app/admin/login` 与登录页 | 「这是演示登录」说明 | ✅ 删除，改成"口令由本机后端持有、首次启动打印一次、也可以自己指定环境变量" |
| `lib/auth/session.ts` | 账号 `admin` + 一个**写死在源码里的固定口令** | ✅ 改为服务端会话（口令在 `server/auth.mts`、令牌在 `lib/auth/token.ts`）。**并且加了回归护栏**：`check.mts` 会扫描前端源码，那个固定口令一旦被写回去立刻红。（这里刻意不再抄写口令本身：它已经失效，写出来只会让人误以为是当前口令） |
| `lib/backend/seed.ts` | 灌入示例学生 / 排课 / 收款 | ✅ 初始状态改成 `lib/backend/initial.ts` 的 `createEmptyDatabase()`（业务表全空 + 网站课程 + 报价配置）；`seed.ts` 降级为**测试/演示夹具**，只有 `NEXGENEDU_ALLOW_SEED=1` 才用 |
| `scripts/check.mts` | 针对 `api.reset()`（重置回示例数据）的断言 | ✅ 改为「清空后业务数据为空、课程库与报价配置保留」；`api.reset()` 的语义也随之改为"清空业务数据" |
| `PROJECT.md` / `docs/技术架构.md` / `docs/使用手册.md` | 「伪后端阶段」的边界说明 | ✅ `PROJECT.md` 的"假登录"一节标注为历史并补了"现状"一节；使用手册换成本机使用与备份说明 |

判据很简单：**任何一句在真实后端下不再成立的话，都必须改掉** —— 留着比没有更糟，
因为它会让员工按错误的前提做事（比如以为换个电脑也能看到数据）。

### 7.2 还剩哪些"暂时不说、将来必须说"的话

清理干净之后仍然有边界，只是这些边界**现在就是真的**，因此照实写出来：

| 边界 | 现状 | 什么时候要改 |
| --- | --- | --- |
| 单用户、无并发控制 | 只有一个账号；两人同时改同一份数据会互相覆盖 | 真要多人用时（那时"操作人"也要改成随请求传递，见 `server/index.mts` 的注释）。**角色与可见范围的对照表**已提前写在使用手册「谁能做什么」一节：普通教师 / 招生老师 / 财务管理员 / 技术管理员（四条的边界已确认，**支持一个账号兼任多个角色**）；落地时按 `lib/backend/contract.ts` 的方法分组在服务端做一处闸门，界面跟着隐藏入口 |
| 会话不落盘 | 后端重启即需重新登录 | 觉得烦时再把令牌落盘（要一起做过期与回收） |
| 令牌放 localStorage | 同源脚本理论上能读到 | 上公网时改 HttpOnly Cookie + HTTPS |
| 只绑本机 | 默认 `127.0.0.1`，局域网访问不到 | 要给别的设备用时设 `NEXGENEDU_HOST=0.0.0.0`（并有意识地接受随之而来的暴露） |
| 快照式存储 | 整库当一份 JSON 存 `kv` 表 | 数据量或并发真成问题时迁到 SQL（接口形状不变，页面不动） |
