# 技术架构

> 读者：将来接手这个仓库的人、以及维护本机服务端（`server/`）的人。
> 如果你只想改内容或使用后台，看 [使用手册](./使用手册.md) 与 [内容维护手册](./内容维护手册.md) 就够了。

**一句话架构**：一个 Next.js 静态导出的网站（`out/`，部署在 GitHub Pages）+ 一个跑在这台电脑上的 Node/SQLite 服务端（`server/`）；教务后台的页面代码没有变，只是它调用的那一层由 `lib/backend/remote.ts` 代理到服务端的 `POST /api/call`，**服务端跑的是同一份 `lib/backend/api.ts`**。

- 网站与后台的数据**不同源**：网站读构建期打包进去的 Markdown 内容；后台读写**服务端 SQLite**（`server/data/nexgenedu.db`，不进 git）。
- 服务端已经接上了（历史：早先所有「服务端应该做的事」都跑在浏览器里，见 [第 8 节](#8-转真后端时改什么)）。业务口径**一行都没有重写**：服务端换的只是存储实现（`server/kv-store.mts` 把整份 JSON 快照写进 SQLite 的 `kv` 表），因此口径天然只有一份。

## 1. 全景

```
构建期（npm run build）
  data/site/*.md
    ↓ npm run sync-content（脚本转成 TS）
  data/site/*.ts（生成物，已提交）
    ↓ lib/data/content.ts 解析（标题层级=结构）
  lib/data/{site,pages,pricing,featured}.ts
    ↓ 页面 / 组件
  out/ 静态产物（79 个页面）

运行期（浏览器）
  宣传网站 app/(site)/*              ← lib/data/*（构建期已打包进来）
  教务后台 app/admin/(dashboard)/*
    ↓ 只调这一层
  lib/backend/api.ts                 当前 110 个方法，全部 async（以 contract.ts 为准）
    ↓ 本机使用时（设置了 NEXT_PUBLIC_API_BASE）换成远端代理
  lib/backend/remote.ts
    ↓ POST /api/call（Authorization: Bearer 令牌）

运行期（本机 Node，默认 127.0.0.1:4000）
  server/index.mts                   HTTP + 一处鉴权闸门 + /api/call 通用分发 + 每天自动备份调度
  server/auth.mts                    口令与会话
  server/kv-store.mts                KeyValueStore 的 SQLite 实现（kv 表存整份 JSON 快照）
    ↓ 服务端跑的是「同一份」lib/backend/api.ts —— 业务口径一行都没重写
  server/data/nexgenedu.db           SQLite；不进 git；每天自动备份（保留 90 份）
```

两条数据链**刻意不交叉**：

- 宣传网站是静态的，家长浏览器里没有后台的数据（服务端默认只绑本机，只由管理员使用）；
- 后台的数据在**服务端数据库**里，改价改了也不会自己出现在网站上：网站读的是构建期内容文件，报价配置要「导出 → 替换内容文件 → 提交」才上线（见 [第 7 节](#7-报价与教师分成)）。

## 2. 三条红线

改动仓库时不要破坏这三条，它们各自都对应过一次真实事故：

1. **页面不解析 Markdown、不读文件。** 页面只调 `lib/data/*` 的访问器。历史上解析器层级写错时，构建依然成功、首页也正常，只有课程正文是空的 —— 靠肉眼发现太晚，因此把解析集中在一处，并让 `npm run check` 覆盖它。
2. **内容改动必须过 `npm run sync-content`。** `data/site/*.ts` 是生成物（同时提交进仓库，这样 CI 不需要先生成就能过类型检查）。手工改 `.ts` 会在下次同步时被覆盖。
3. **后台的一切改动必须走 `lib/backend/api.ts`。** 页面不直接读写存储；`export type BackendApi = typeof api` 是那份唯一的形状，而**服务端跑的就是这一份实现**（换的只是存储与调用方式），所以这条红线现在同时守住了「前端与服务端口径一致」。

## 4. 内容管线

### 4.1 解析器：标题层级即数据结构

`lib/data/content.ts` 把一个 Markdown 文件解析成「页面 → 分组 → 节 → 条目」：

```md
# NexGenEdu · 新锐教培                     ← 文档标题

## 页面: 课程                              ← 页面边界

---
title: 课程                                ← 页面字段（--- 包裹的键值块）
---

### 小学课内                                ← 分组

#### 小学语文 | 路径: primary-chinese        ← 条目（| 后是字段）

正文段落…
```

设计要点：

- **不引 Markdown 库**：结构完全由标题层级决定，因此「内容里少写一个 `#`」只会丢内容、不会让构建失败；相应地，自检必须覆盖结构。
- **容错优先**：解析器遇到不认识的块只记警告、不抛错（构建不能因为一段内容写歪就整站挂掉）。
- 字段块用 `---` 包裹；`- · 字段: 值` 是卡片正文里的元数据行。

### 4.2 为什么 `.md` 还要生成 `.ts`

`·`（U+00B7）经过 webpack 会被序列化成非法转义 `\xb7`，导致内容在运行时坏掉。因此内容在构建前由 `scripts/sync-content.mjs` 转成 TypeScript 字符串模块。生成物同时提交：这样 CI 与类型检查不依赖「先生成」，也便于在 PR 里看清内容改了什么。

## 5. 宣传网站

- **静态导出**：`next.config.ts` 里 `output: "export"`、`trailingSlash: true`、`images.unoptimized: true`；子路径部署由 `NEXT_PUBLIC_BASE_PATH` 注入 `basePath`/`assetPrefix`。
- **页面全部静态**：没有服务端渲染、没有 API 路由，网站**产物**不连任何数据库 —— 访客的浏览器不会为了看课程介绍去请求后端。报价页的计算也在浏览器里进行。
  （网站**内容**的来源是另一件事：构站那一刻可以以后端库为准，见下面 §5.1。教务后台的数据在服务端 SQLite 里，那是本机单独跑的进程，不进 `out/`。）
- **课程的三层结构**：`/courses`（6 个栏目 → 卡片）→ `/courses/<栏目拼音>`（学段页）→ `/courses/<卡片 slug>`（一张卡片一个页面，卡片内的「标签」是同一页面里的不同阶段，不单独成页）；特色课程在 `/courses/featured/<path>`。
- **404 与链接**：`check-404.mjs` 校验产物里的 404 分流与样式；`check-links.mjs` 遍历产物中所有站内链接（当前 2544 个）确认都有对应文件。

### 5.1 网站内容从哪来：那五块「连上后端用库、连不上就空白」

宣传网站的内容分**两类**，规则不同：

| 类别 | 内容 | 来源 |
| --- | --- | --- |
| **库里才有的（"那几块"）** | 教师页 · 课程卡片 · 课程正文 · 报价 · **学生案例** · **特色课程** · **常见问题** | 连上后端 → 用库里的；没连上 → **骨架在、条目空**（见下） |
| **只在模版里的** | （已全部搬进库；`data/site/*.md` 现在的角色是"没连后端时的骨架来源"与迁移初值） | 见下表的 `blank` 一列 |

那五块的取值只有三种，判据一处（`siteContentSource()`，见 `lib/site/backend-source.ts`）：

| 取值 | 什么时候 | 那几块 |
| --- | --- | --- |
| `backend` | 构站这台机器**连得上后端**（拿到一份结构合法的 `GET /api/public/site`） | 用服务端数据库（`server/data/nexgenedu.db`） |
| `blank` | **连不上**（没起后端、超时、非 200、结构不对）—— **默认行为** | **骨架来自模版、条目为空** |
| `template` | 显式 `SITE_CONTENT_SOURCE=template` | 整份用 `data/site/*.md`（本地对照 / 确实要发一份模版站时） |

### 页面文案块：五块共用一套模型与一个读取接口

品牌与联系方式、首页、关于我们、联系我们、课程时间安排这五块形状完全一样 ——
**短字段（键 → 值）+ 若干分组（分组标题 + 条目）**，因此它们共用一个模型
（`SiteCopyBlock`）与一个读取接口（`CopySource`，见 `lib/backend/site-copy-model.ts`）：

```
模版（data/site/*.md 解析结果） ─┐
                                ├─→ CopySource ─→ brandFrom / homeFrom / aboutFrom / contactFrom / scheduleFrom
库（siteContent.copy[key]）    ─┘                （**一份映射，两种来源**）
```

**为什么这样设计**：两处各写一遍字段映射（`pageString(page, "phone")` 与 `field(block, "phone")`）
必然会漂 —— 改了一边的字段名、另一边还在读老名字，而**两边都返回空串、谁也不会报错**。
共用映射之后，"两条来源产出同一份页面数据"从"需要断言"变成了**结构上不可能不同**；
自检里那六条等价断言是把它钉住（并且抓出过一次真错：`trial_points` 的竖线分隔符，
当时页面上的 ✓ 位置变了，只有逐页 diff 才看得出来）。

其余三块（案例 / 特色课程 / 常见问题）各有自己的结构（列表、树、分组问答），因此没有并入这个模型。

### `blank` 到底空什么：**骨架在、条目空**

机构先后给了两句，合起来才是完整口径：

1. 「需要用到后端数据的部分应该是空白的」→ **条目为空**，不拿模版顶上。
   拿模版顶上会让人分不清页面上看到的到底是库里的还是文件里的 —— 而那正是要消灭的东西；
2. 「教师界面和学生案例不能全空，得有分区标题」→ **骨架照常显示**：页面眉题 / 标题 / 说明、
   **分区标题**（FAQ 的分组标题、课程页的「特色课程」「课程总览」）、页脚提示、报价页那些
   按钮与标签文字 —— 它们属于"页面长什么样"，来自 `data/site/*.md`。

哪一部分空、哪一部分在，逐个说清：

| 块 | `blank` 时保留（来自模版骨架） | `blank` 时为空 |
| --- | --- | --- |
| 教师页 | 眉题 / 标题 / 说明 | 教师列表（另有一句「暂无展示中的教师」） |
| 课程页 | 页面标题 / 「特色课程」「课程总览」的区块标题与说明 | 栏目、卡片、学科正文、选修分组 |
| 报价页 | 页面标题 / 按钮与标签文案 / 计费规则说明 | 阶段、科目、班级类型、时长、其他项目 |
| 学生案例 | 眉题 / 标题 / 说明 / 页脚提示 | 案例列表（另有一句「案例整理中」） |
| 特色课程 | 眉题 / 标题 / 说明 / 页脚提示 | 课程树（另有一句「特色课程整理中」） |
| 常见问题 | 眉题 / 标题 / 说明 / 页脚提示 / **全部分组标题** | 每组的问答（组内另有一句「这一组暂时没有问题」） |
| 品牌与联系方式 | **整份**（站名 / 口号 / 电话 / 微信 / 地址 / 营业时间 / 上课时间 / 备案…） | 无（这一块全是"网站自己的身份"，没有条目可分） |
| 首页 | 全部短字段（hero / 各区块标题 / 按钮 / 试课要点） | 「首屏数据」「教学特色」「教室照片格位」三组里的条目 |
| 关于我们 | 全部短字段（标题 / 理念 / 服务标题 / 校区标题） | 「服务形式」「教学理念」「校区数据」「校区介绍」四组里的条目 |
| 联系我们 | 全部短字段（标题 / 路线说明 / 按钮文案） | 「联系方式清单」里的条目 |
| 课程时间安排 | 全部短字段 + **每个分组的标题与说明** | 各分组的时段条目 |

> **两句都要守住**：只守第 1 条会得到"整页空白"（机构看到后当场反馈"不能全空"），
> 只守第 2 条就退回"拿模版当数据"。自检第 25 / 28 节分别盯着这两条。

**三条纪律**：

1. **判据只有一条**：`siteContentSource()`。取数发生在 `lib/data/*.ts`，每个函数一次三选一 ——
   没有 `backendX() ?? 模版` 这种逐块回落（那会让同一页一半来自库、一半来自文件）。
   骨架的保留规则写在上面那张表里（**分区块标题要留着，条目的空要说一句话**）；
2. **"数据不全"不等于"连不上"**：体检只看**结构**（缺 `teachers` / `courses` / `partitions` /
   `siteContent.coursePage` / `pricing.stages` 才算连不上），内容多少不参与判定；
   连上了但某块是空的 → 就按空显示（日志里点名）；
3. **模版那一态只能显式要**：`SITE_CONTENT_SOURCE=template`。默认的 `auto` 在连不上时
   写的是 `blank`，"悄悄用模版"这条路径不存在。

**判定发生在一处**，就在 `npm run build` 之前：

```
npm run sync-content    → data/site/*.ts             （Markdown → 可 import 的模块）
npm run sync-site-data  → data/site/.backend-snapshot.ts（去问一次 GET /api/public/site）
                          写出 backendSiteSnapshot（数据）
                          + backendSiteSource（backend / blank / template）
next build              → 页面按上面的结果生成
```

- `scripts/sync-site-data.mjs` 打印一行「本次网站数据来源：**后端** / **空白** / **模版**」，
  并在用后端时**逐块报数**（教师 / 卡片 / 分区 / 学科 / 小节 / 报价阶段 / 选修课），
  空块单独 ⚠ 列出来 —— 这是"这一块为什么是空的"唯一的线索；
- 这类功能最容易出的隐形故障是"以为在用后端，其实用的是模版"，页面上看不出来，所以每次构建都留痕；
- ⚠️ **`SITE_CONTENT_SOURCE` 要设在 `npm run build` 那一步上**：`build` 内部会再跑一遍
  `sync-site-data`（见 `package.json`），那个子进程**不继承**前一步的 env ——
  只设在单独一步上，会被后面这次用默认 `auto` 重新判定并覆盖掉
  （GitHub Pages 的工作流就是两处都写了，注释里说明了原因）。

**内容在哪一侧维护**（这一条最容易搞错，写清楚）：

| 内容 | 归谁 |
| --- | --- |
| 教师资料、课程卡片、**课程分区（栏目 → 子栏目）**、课程正文、报价（数字与文案） | **库**（后台改；老库点一次「课程库 → 从网站导入内容」补齐） |
| **学生案例**（`/cases` 与首页那块） | **库**（v19 起；后台「网站内容」页增删改，技术管理员 + 招生老师） |
| **页面文案**：品牌与联系方式、首页、关于我们、联系我们、课程时间安排 | **库**（v22 起；后台「网站内容」页五个页签，技术管理员 + 招生老师） |
| **特色课程**（三级课程树 + `/courses/featured/**` 页面） | **库**（v20 起；后台「网站内容」页增删改与调顺序） |
| **班型**（课程表单那五处下拉、报价的班级系数） | **库**（v23 起；后台「课程类型」页。全系统唯一口径 = `catalog.formats`：一对一 / 一对二 / 一对三 / 一对多（4-8）/ 班课（9-20），与 `pricing.md` 的「班级类型」逐个同名）。v23 之前取的是特色课程的二级课程名（一对一定制课 / 一对三小组课…），两套写法已废弃 |
| `data/site/*.md` | **只在模版里那几块的唯一来源**（首页 / 关于 / 联系 / FAQ / 课表 / 特色课程），也是一次性导入与**迁移初值**的来源；显式 `SITE_CONTENT_SOURCE=template` 时也是那五块的来源 |
| 首页 / 关于 / 联系我们 / 常见问题 / 时间安排 / 特色课程这些页的文案 | 仍是模版（**正在分批搬进库**：见 PROJECT.md 的计划，B0 已完成的是学生案例） |

改完库里的内容要**重新构站**才会反映到网站上。GitHub Pages 那份是 Actions 构的、
那台机器上没有后端 —— 按默认口径**那五块是空的**（教师页 / 课程页 / 报价页 / 案例页没有内容）。
想让 Pages 显示模版内容，就把工作流里的 `SITE_CONTENT_SOURCE` 显式设成 `template`
（`deploy-pages.yml` 里有注释说明两种选择的后果）。

**两条数据路径必须等价**，这一条由自检与一个专门的门禁守着：

- `npm run check` 里有四条等价性断言：把示例库转成快照注入后，
  `getTeachersPage` / `getCourseColumns` / `getCoursesPage` / `getPricingData`
  必须与模版那条路**逐字相同**（另有"导入侧永远读模版、不读快照"的断言）；
- `node scripts/compare-site-builds.mjs <产物A> <产物B>` 比两份构站产物的**页面正文**：
  同一份内容下，后端模式与模版模式构出来的页面应当逐字相同（资源哈希必然不同 ——
  后端模式的产物里内嵌了那份快照数据）。

## 6. 服务层（`lib/backend/`）与服务端（`server/`）

### 6.1 分层

同一份服务层，换一个存储实现就同时是「浏览器里的实现」和「真实服务端」：

```
页面（客户端组件）
  ↓ 只调这一层，方法签名与 REST 一致、全部 async
lib/backend/api.ts     当前 110 个方法（以 contract.ts 为准）：CRUD / 关联查询 / 业务动作 / 咨询 / 报价 / 看板 / 运维
  ↓ 本机使用时这一层换成远端代理（页面、类型、方法名都不变）
lib/backend/remote.ts  每个方法 → POST /api/call（Bearer 令牌）；服务端跑的还是上面那份 api.ts
  ↓
lib/backend/storage.ts  KeyValueStore 抽象（read / write / remove）
  ↓ 三种实现，上面那份 api.ts 直接跑在它们之上
  · 浏览器：localStorage（键 nexgenedu.admin.db.v1）
  · 自检：内存实现
  · 服务端：server/kv-store.mts（SQLite 的 kv 表，存同一份 JSON 快照）
  ↓ 存储为空时灌入初始状态
lib/backend/initial.ts  初始状态＝空库（业务表全空 + 网站课程 + 报价配置）
lib/backend/seed.ts     示例数据：只是自检/演示夹具，要 `NEXGENEDU_ALLOW_SEED=1` 才灌
```

`types.ts` 是数据契约（`Student`/`Teacher`/`Classroom`/`Lesson`/`Payment`/`Enrollment`/`Inquiry`/`PricingConfig`/`Catalog`…），`version.ts` 是结构版本（**当前 v23**），`contract.ts` 是接口清单与「服务端必须自己复核的校验」。

**初始状态与示例数据分开，是接上服务端时特意做对的一件事**：机构真正开始用的起点必须是一张白纸（早期 `load()` 在存储为空时灌示例学生，员工会以为那是自己录的数据），而 `seed.ts` 只服务自检与演示。`api.reset()` 的语义也与此对齐 —— 它清空的是**业务数据**，保留网站课程与报价配置。

### 6.2 领域纯函数模块

业务规则全部抽成**不碰存储的纯函数**，因此既能在浏览器里跑，也能在 Node 里被自检完整验证，并且**原样搬到了服务端**（因为它们本来就不依赖存储）：

| 模块 | 职责 | 关键约定 |
| --- | --- | --- |
| `enrollment.ts` | 报课记录、剩余课时 | 剩余 = 有效正向流水 − 已用 |
| `finance.ts` | 金额、退费口径 | 实收 = 收款合计 − 退款合计；`REFUND_POLICIES` 两种口径，默认 `prorata`（按实付比例退） |
| `attendance.ts` | 出勤与请假扣课时 | `LEAVE_NOTICE_HOURS = 24`：提前 24 小时请假不扣，临时缺课扣 |
| `followup.ts` | 待跟进信号与话术草稿 | `FOLLOWUP_RULES`：剩余 ≤5 提醒 / ≤2 紧急、7 天未排课、作业未交 2 次、旷课 1 次、分数下降 10 分… |
| `stats.ts` | 经营视图 | `CLASS_HOURS_PER_DAY = 14`（上课时间 8:00–22:00 口径，不是营业时间 9:00–21:00）；利用率 ≤ 1 |
| `inquiry.ts` | 咨询可行性判定 | **检查的是一整串日期**，不是一天；判定只看不改，落库前再复核一次 |
| `pricing.ts` | 报价配置、公式、校验、导出 | 公式**只有这一份实现**；报价只收「选择」不收价格 |
| `teacher-share.ts` | 教师课时费（分成） | `小时数 × 课程单价/小时 × (0.4 + (人数−1) × 0.1)`；按计价方式判定适用范围 |
| `search.ts` | 全局搜索 | 只做不区分大小写的子串匹配，刻意不做拼音模糊 |
| `backup.ts` | 导出/导入校验、条数统计 | 导入三道保险：结构校验 → 自动备份 → 版本迁移 |
| `availability.ts` | 教室可用时段 | 不在开放时段内的排课被拒绝并说明原因 |
| `student-profile.ts` | 学生信息采集表字段定义 | 键值对存储，加字段不需要迁移 |
| `options.ts` | 后台表单候选项 | **从站点内容与课程类型取**（科目、班型、标准时段），不另抄一份；班型的同步种子来自 `catalog-seed.ts` 的 `formats`，挂载后由 `useFormOptions` 换成库里的那一份 |
| `catalog.ts` | 课程类型的校验与派生（**纯函数**） | 三个读者共用：`catalog.save` 的闸门、后台「课程类型」页、以及以后要做的组合解析（AI 排课 / 诊断推荐）。重名判据是**同一层内**（模块先按「学科 + 上级」分组再判）；`subjectsInGroup` 实现「分组是学段内的桶」 |
| `catalog-seed.ts` | 课程类型的种子（机构那份分类清单） | 逐行转录 + **展开时合并**：同名学科合并成一行、学段取并集 —— 清单里「小学语文 / 初中语文 / 高中语文」是**一行**语文 × 三个学段。id 由名字派生（确定性、可重复灌） |
| `format.ts` | 日期时间与金额格式化 | 全站统一，避免各处各写一套 |

### 6.3 数据不变式（自检逐条盯着）

- 报课实收 = 收款合计 − 退款合计；
- 已用课时 = 有效「上课」流水合计；总课时 = 有效正向流水合计；
- 教室利用率 ≤ 1；
- 课时、收款、流水**留痕不删**（撤销是写反向记录，不是删行），只有档案类允许真删；
- 每一次影响课时/金额的改动都要落操作日志（含摘要）。

### 6.4 迁移纪律（踩过的坑）

- 版本号只有一个来源：`version.ts` 的 `CURRENT_VERSION`，夹具（`seed.ts`）与迁移逻辑都必须用它（曾因 seed 写旧版本，导致刚灌入的新数据在下次读取时被当成旧数据迁移，把报课记录压成一条「未指定科目」）；
- `migrate()` 里的分支**必须按版本升序排列**（曾写反顺序，v1 数据停在 v3、`migrate()` 返回 null，整库被当成坏数据重新灌种子）；
- `migrate()` 是就地修改，比较版本号要在改动**之前**记下来；
- 老库缺新字段时补默认值，**不要让字段是 `undefined`**（v10 → v11 就是给报价配置补教师分成规则）；
- 接上服务端后多了一条：**迁移前服务端会先备份**（`server/migrate.mts` 调 `backupTo`，产出 `nexgenedu-migrate-<时间戳>.db`），且自检/演练起的临时库**不参与备份**（`NEXGENEDU_NO_BACKUP=1`）—— 否则临时库的空备份会挤掉真实库当天的那一份。

#### 迁移失败**绝不覆盖**（2026-09 审计）

`load()` 早先的写法是"读不出来就当首次访问"：`migrate()` 返回 null（版本比当前新、或某个分支卡住）
或 JSON 解析失败时，直接 `createEmptyDatabase()` 并**落盘覆盖**。实测过一个真实场景：
一份结构正常、只是版本号写着 1 或 2 的库，读一次就变成空库，而且不可逆 ——
根因是 v2 分支把"要不要做结构变换"和"版本号推进到哪"混在一个条件里，
结构已是新版时版本号不推进，后面每个分支全部跳过，`migrate()` 返回 null。

现在的口径（两条一起才成立）：

1. **分支只管变换，版本号无条件推进**（v2 分支拆成 `if (version === 2) { if (需要变换) {…} db.version = 3 }`）；
2. **有内容却读不出来 → 抛错、什么都不改**，错误里说清"本次没有改动任何数据、请用备份恢复"。
   空库起步只允许发生在"存储里确实没有内容"这一种情况。

自检第 17 节把这两条都钉住了：v1/v2 + 新结构读一次之后**学生数与收款数一条不少**、
版本号被推进到当前版本；坏 JSON 与"版本比当前新"两种情况下，存储里那串内容**一个字节都不许变**。

### 6.5 服务端（`server/`）

服务端默认只绑本机（`127.0.0.1:4000`，`NEXGENEDU_HOST` 可改），起点命令是 `npm run server`。

| 模块 | 职责 |
| --- | --- |
| `index.mts` | HTTP 服务、`/api/call` 通用分发、**一处鉴权闸门**、**账号管理四条路由**（`/api/accounts`，技术管理员专属）、每天自动备份调度、`Date` 参数解码（`{__date:ISO}` 显式标记） |
| `accounts.mts` | 账号表（`accounts.json`，0600，含明文口令；与凭证文件同目录）：登录校验、角色、`disabled`（停用）、加人 / 改角色 / 重置口令 / 删除（写盘只改那一条、写完清缓存立刻生效） |
| `auth.mts` | 口令来源（`NEXGENEDU_ADMIN_PASSWORD`，否则首次启动随机生成写入 `server/data/admin-credential.json`，权限 0600 且只打印一次；口令**不进数据库**）、口令校验（scrypt + 定长比较）、会话签发与作废 |
| `kv-store.mts` | 在 SQLite 的 `kv` 表上实现 `KeyValueStore`：整份 JSON 快照一个键（`nexgenedu.admin.db.v1`） |
| `db.mts` | 连接（WAL）、备份原语（`VACUUM INTO`）、**备份命名规则**（备份、迁移、清理共用同一个函数，否则「哪份最新」会算错） |
| `migrate.mts` | 迁移器：跑迁移链，**迁移前备份**；没有待应用迁移时不备份 |
| `backup.mts` / `backup-cli.mts` | 每天一份、容量与保留份数（默认 **90** 份 ≈ 三个月）、`npm run server:backup` 手动备份 |
| `import-data.mts` / `reset-data.mts` / `clear-payments.mts` | 运维脚本：导入旧导出、重置成空库起步、清理收款数据 |

**端点**（公开的只有三个：`/health`、`/api/login`、`/api/logout`；`/api/session` 免闸门，但没有令牌时一样回 401）：

| 端点 | 方法 | 要不要登录 | 说明 |
| --- | --- | --- | --- |
| `/health` | GET | **公开** | 只回 `{ok, service, db, authRequired}`；自检与演练靠 `db` 字段确认「应答的确实是本次这个进程」，界面靠 `service` 确认「这是本系统的后端」而不是端口上的别的程序 |
| `/api/login` | POST | 公开 | `{username,password}` → `{ok,token,username,expiresAt}`；失败一律 401，且**不区分**「账号不存在」与「口令不对」 |
| `/api/logout` | POST | 公开 | 带 Bearer → 作废该令牌 |
| `/api/session` | GET | 无令牌即 401 | 带 Bearer → `{ok,username}`，前端用它问「我是谁」 |
| `/api/status` | GET | 要登录 | 数据库路径、结构版本与迁移结果、各表条数、备份状态、会话数 |
| `/api/call` | POST | 要登录 | `{method,args}` 通用分发，**页面走的就是这一个入口** |
| `/api/accounts` | GET / POST / PATCH / DELETE | 要登录 **+ 技术管理员** | 账号管理（后台「账号」页）：列表 / 新建 / 改动 / 删除。**刻意不是 `/api/call` 的方法**（账号表是服务端进程里的文件，服务层在浏览器里也跑），因此它不在 `API_CONTRACT` 里、角色判定在路由内（`accountsRouteDenial`）。响应里绝不含口令与哈希；最后一位技术管理员不能被删 / 降级 / 停用；`NEXGENEDU_ACCOUNTS_JSON` 下拒写，详见 [后台API约定 §7.1](./后台API约定.md) |
| `/api/students` 等 | GET | 要登录 | 路线 A 的参考 REST 接口：读写的是它自己那套 SQL 表，**不在页面用的数据通路上** |

鉴权是**结构性**的：`/api/` 下除上面列出的公开入口外一律要登录（一道闸门），逐个接口加鉴权会漏 —— 第一版就漏了读接口 `/api/students`，未登录返回 200 把学生数据交了出去。令牌存在服务端内存里、闲置 12 小时过期、**后端重启即失效**；操作人由服务端按会话记录，前端说了不算。

### 6.6 课程类型：五个维度，而不是一份课程清单（v23）

机构给的那份课程分类清单铺开有 **400 多条叶子**，但把它们读一遍会发现：那些叶子全是
**五个维度的乘积**。

```
学段（5） × 学科 / 项目（38） × 内容模块（98） × 班型（5） × 交付形态（5）
```

**为什么不能枚举**（这是这一版改动的全部理由）：

- 加一个语种、加一级等级，记录数就翻倍；
- 改一次班型名字要在几百条记录里改一遍；
- AI 排课与诊断推荐只能靠「一个诊断项硬绑几门课」来对付，而"这个学生的短板是阅读"与
  "这个学生的短板是文言文"在枚举表里长得一模一样。

维度法的做法：**维度是数据，组合按需解析**。哪一条组合开放、按什么价，在 P2 的「开放矩阵」
里勾（那一步要等维度表稳定，否则矩阵的行列天天变）。

#### 五个维度各自是什么

| 维度 | 表 | 说明 |
| --- | --- | --- |
| 学段 | `catalog.stages` | 小学 / 初中 / 高中 / 大学 / 其他类型。机构清单的第一层 |
| 学科与项目 | `catalog.subjects` | **学科与学段解耦**：清单里「小学语文 / 初中语文 / 高中语文」是**一行**语文 + 三个学段。「小升初预习班」「托管」这类是 `项目`；`parentIds` 支持一层分组（外语等级考试 → 雅思） |
| 内容模块 | `catalog.modules` | 属于某个学科。分三类（`kind`）：`教材进度`（一年级…九年级 / 必修选修）、`能力点`（客观题 / 阅读 / 文言文 / 作文 / 听力）、`语言等级`（CEFR-A1…B2 / N5…N1 / CET-4·6）。**诊断推荐按类别筛** |
| 班型 | `catalog.formats` | **全系统唯一口径**：一对一 / 一对二 / 一对三 / 一对多（4-8）/ 班课（9-20），与 `data/site/pricing.md` 的「班级类型」逐个同名。带 `minSize` / `maxSize` 与计价模式（`系数` / `分摊`） |
| 交付形态 | `catalog.deliveries` | 课怎么上：面授 / 网课 / 网课+答疑 / 托管 / 全日托管。**与班型正交**（一门课可以面授也可以网课+答疑） |

`seededAt` 记着这份维度表是照哪一版种子灌进来的（"要不要重新灌"的判断依据）。

#### 三条容易搞错的口径

1. **合并**：种子（`catalog-seed.ts`）里那份 `SUBJECTS` 是清单的逐行转录
   （同名学科会在每个学段各出现一次），展开时**按名字合并成一行**、学段取并集。
   不合并的话 id 会重复 —— 而报价 / 排课 / 诊断引用的是**学科 id**，
   "小学的那条语文"与"初中的那条语文"就分家了。模块同理，而且合并范围是**整个学科**：
   语文的「客观题」在初中与高中各写了一遍 → 合成一行 `能力点`，`stageIds` 是 [初中, 高中]。
2. **重名的层级**：学段之间、学科之间、班型之间是同一层（同一个下拉），重名没法选；
   模块与学科是两层 —— 两个学科各有一个「听力」是两条互为独立的模块（模块不跨学科复用），
   因此重名判据是「同一个学科 + 同一个上级」。
3. **分组是学段内的桶**：「日语」在高中是高考外语（直接挂在学段下），在「其他类型」里又在
   「外语等级考试」下（N5…N1）。因此 `parentIds` 是一个**列表**，而"它属于哪个分组"只在
   **该分组也属于当前学段**时才生效；否则退回顶层显示（`subjectsInGroup`）——
   不做这条的话，"高考外语里有日语"在高中那一栏会整条消失。

#### 读写的形状：整份读、整份写

`catalog.list()` / `catalog.save(input)` / `catalog.resetToSeed()` 各一个，
**不做五张表各一套 CRUD**：维度表是**配置**（几百行），页面上的操作就是
"在这份草稿上改 → 一次保存"，整份替换不会出现"改了三处、只有两处落库"。
代价是两个人同时改会以后保存的为准 —— 日志里记下规模变化（`原 5 个学段 / …`），
出问题看得出是哪一次改的。

新行的 id 由**保存前的一次扫描**补（`assignCatalogIds`，id 是那一刻名字的函数）：
新增时就生成的话，"改名"要么把引用它的 `stageIds` / `parentIds` 一起指丢，要么 id 与名字不一致。
模块的 id 还带学科名（`mod_英语·听力`），因此不能走通用填充 —— 这条正是自检第 30 节抓出来的。

#### 后台「课程类型」页

五个页签一屏一个（学段 / 学科与项目 / 内容模块 / 班型 / 交付形态），每行可改名 / 换类别 /
勾学段 / 分组 / 排序 / 删除，右上角「新增」，底部「保存修改」与「恢复种子」。
校验实时显示（`validateCatalog` 在前端与服务端是**同一份**）：红字出现时保存按钮是灰的。
学科与项目按分组分节展示（编辑要一次看全，所以不按学段分层）。

**权限**：`crud` 分组（技术管理员 / 财务管理员 / 招生老师），普通教师只读 ——
教师要用「班型」下拉，但"本机构开哪些班型"不该由每位老师各改一份。

### 6.7 开放矩阵：本机构开哪些组合（v24，`offers`）

维度表回答"**可以**有哪些维度"；这一张回答"本机构**开哪些**组合"：

```
一条组合 = 学科 × 内容模块 × 班型 × 交付形态
        （例如「语文 · 客观题 · 一对一 · 网课+答疑」）
```

**为什么是稀疏存储**：把全部组合铺成行是 136 个（学科 × 模块）格 × 5 班型 × 5 交付
= **3400 条**空行，而机构真正开的通常只是其中一小片。因此只有"机构表过态"的组合才有行 ——
于是有**三种状态**，而这三件事必须分开：

| 状态 | 数据 | 含义 |
| --- | --- | --- |
| 开放 | 有行，`open: true` | 明确开 |
| 明确关闭 | 有行，`open: false` | 机构**表过态**：不开（"这个班型不做网课"） |
| 没设置 | 没有行 | 还没人想过这件事 |

为什么保留"明确关闭"而不是删行：维度表一改（加一个班型、加一个模块），"没设置"的格子会
一片片冒出来 —— 那正是需要机构回来看一眼的信号。关闭也记下来，才能让"已决策"与"待决策"
在矩阵里一眼分开。

**组合的身份是那四个 id**（`offerId` = `off_` + 四个 id 拼起来）：同一条组合不可能有两行，
批量勾选不必先查重，维度改名也不影响它（全系统按 id 引用）。⚠️ 这个键**只当键用、绝不反解**
—— 模块 id 自己就带 `·`（`mod_语文·客观题`），按下标切分必然切错；要拿四个取值就从
`OfferRow` / `OfferColumn` 的结构体上拿。

**矩阵的形状**（四个维度、表格只有两维）：

```
          一对一            一对二        …
        面授 网课 答疑 …    面授 网课 …
语文         ✓    ✗
（不分模块）
  一年级     ✓    ✓
```

- 行 = 学科 + 它的模块（`moduleId` 空的那一行＝"不细分模块"，它**是合法的一条**，
  不是缺省：诊断推荐才需要模块那一层）；
- 列 = 班型 × 交付形态；
- **学段不进组合键**，只用来筛行（学段 + 学科 + 模块已经唯一确定一门课 ——
  小学语文的一年级 ≠ 初中语文的一年级，因为模块各自挂在学科下）；
- **分组（"外语等级考试"那样的桶）不出现在行里**（它是桶，不是能开课的学科）。

**批量勾选的实现**：`applyDecision(offers, keys, decision, now)` 是纯函数
（`lib/backend/offers.ts`），页面上的"整行 / 整列 / 整个学段 / 全部"都只是"键的集合不同"。
因此服务端只有 `offers.list` / `offers.save` 两个方法 —— 不为每种批量动作加接口，
也就不会出现"单条能存、批量被拒"。

**格子点一下的循环**：没设置 → 开放 → 明确关闭 → 没设置。只剩两个状态的话，
机构按错一次"全选"就再也擦不掉了。

**它给谁用**：AI 排课与诊断推荐按 `resolveOffer(index, key)` 判定一条组合开不开
（`open` / `closed` / `unset` 三种答案都要处理 —— `unset` 不等于"关"，
推荐时要把它当成"要先问机构"）。**价格不在这张表**：课程价与班型系数仍在报价配置里，
把价搬进来会让同一门课出现两个价源。

### 6.8 班型的名字只有一个真源（v25）

维度表（§6.6）把「班型」收成了一份数据，但**报价配置里仍然各自记着一份名字**：
`data/site/pricing.md` 的「班级类型」给每个班型一个系数，那一节里写着班型的名字。
机构在「课程类型」页把「班课（9-20）」改成别的写法后，报价页与网站报价器上还是旧名字 ——
而**这种不一致不会报错**（两边都显示得像正常的），家长问价时才发现对不上。

v25 的做法：**名称与人数区间以维度表为准，报价只保留"这个班型多少钱"**。

| 问题 | 答案 |
| --- | --- |
| 身份是什么 | 报价的每一行班级类型带 `formatId`（指向 `catalog.formats`）。迁移（v24 → v25）按名字给老数据补上这个字段 |
| 名字从哪来 | 读的时候由 `syncClassTypes` 换成维度表里的当前名字（`api.pricing.get` / `buildPublicSite` / `exportMarkdown` 三处共用同一个纯函数）；`catalog.save` 落库时也一起对齐（库里不留过期名字） |
| 改名会怎样 | 报价页、网站报价器、导出的 `pricing.md` 一起变。引用它的地方（课程、报课、排课）只认 id，不受影响 |
| 试算会不会失败 | 不会：`pricing.quote` / `pricing.teacherFee` 用**对齐后**的配置查班型 —— 页面发过来的是新名字，而库里那一份可能还没跟上 |
| 对不上怎么办 | 两种差异都会在报价页提示（`classTypeIssuesText`，一句话说清后果）：**报价里有、维度表里没有**（`orphans`，那一行已经不会被任何课用到）与 **维度表里有、报价里没有**（`unpriced`，新班型还没有系数 —— 家长问到它时算不出价）。对不上的行**原样保留**，不静默丢一行价格 |
| 保存时拦什么 | `pricing.update` 拦住 `formatId` 指向不存在的班型（那一行系数永远算不到，而页面看起来一切正常），以及同一个班型挂两行系数（"这个班型算哪一行"会两说） |
| 静态那一份怎么办 | `data/site/pricing.md` 里的班型名必须等于维度表的种子（`catalogFromSeed().formats`）—— 自检第 30 节把这条钉住；导出 Markdown 时用的也是维度表里的名字，因此下一次构站不会漂回去 |

## 7. 报价与教师分成

价格是**数据**，不是常量：

- 配置类型 `PricingConfig` 存在数据库里（基础价、科目系数、班级系数、时长乘数、手续费、试课门槛、教师分成规则），随备份一起迁移；
- 公式只有一份实现（`lib/backend/pricing.ts` 的 `calculateQuote`）：前台报价页与后台试算器调的是同一个函数 —— 「宣传页一个价、后台另一个价」是这一块最不能出的事故，自检里有 7 个用例逐个比对两边算出的数；
- `lib/pricing/quote.ts` 只是站点侧的薄适配（取内容里的规则转发给后端公式）；
- 内容里的「计费规则」「教师分成」分组与后台配置是**同一个形状**：`api.pricing.exportMarkdown()` 导出的片段可以直接替换进 `data/site/pricing.md`，自检会把导出结果回读一遍，确认它与后台配置一致。

**这是一个还没消失的限制**：后台配置存在**服务端数据库**里，而家长看到的报价页是静态的、读构建期内容文件 —— 两者没有同步通道。所以「后台改价 → 家长看到」之间仍然必须有人做一次「导出 → 替换内容文件 → 提交」。

（历史：早先后台数据在管理员那台浏览器里，那一步同样是必需的；接上服务端并没有顺带解决它，因为网站是静态导出。要真正消失，得让网站内容进库做只读镜像，见第 10 节「还没做」。）

> **现状：✅ 已经做过一次** —— 本节是"当时计划怎么改"的记录。
> （结论写在这里而不是写进标题，是因为标题里加「已做过」会让别处指向本节的锚点变成死链，
> 而自检现在会校验同一份文档内的锚点。）
> 这一步已经落地了，走的是"服务端复用同一份 `api.ts`"的路线（
> [后端开发方案](./后端开发方案.md) §5.3 的路线 B）：服务端换一个 `KeyValueStore`
> 实现（SQLite 的 `kv` 表）+ 一个通用分发路由 `/api/call`，
> 于是**业务口径一行都没重写**。后来又在上面加了服务端会话认证（§5.6）与
> 每天自动备份（§6），并用 `npm run check:both` 证明了"两种后端跑同一套断言结果一致"（§5.7）。
> 下面这段是**当时**计划怎么改的，保留下来对照用。

完整清单在 [后台API约定.md](./后台API约定.md) 与 `lib/backend/contract.ts`（当前 110 个方法按「服务端怎么做」分成 7 类）。要点（**下面每一句都是当时写下、后来被验证过的**，✅ 表示已经做完）：

1. ✅ **前端只改一个文件**：对外形状由 `export type BackendApi = typeof api` 固定，页面代码一行没动。实际做法与最初设想不同：`api.ts` 的实现**没有**从 localStorage 换成 `fetch`，而是新增一层 `lib/backend/remote.ts` 把 `api` 的每个方法代理到 `POST /api/call`（由 `NEXT_PUBLIC_API_BASE` 决定导出哪一份），服务端则整份复用 `api.ts`。这条路线的好处是「同一个方法签名被手写两遍」的风险不存在 —— 手写 fetch 版本时漏一个方法、猜错一个字段名都是**静默**出错；
2. ✅ **服务端必须自己复核的 12 项校验**（冲突、容量、幂等、课时非负、金额不变式、退费重算、请假判定用服务端时间、鉴权、审计、课程名唯一、报价配置合法性、报价金额由服务端算）—— 每一项都对应一个已经踩过的坑。现在这些校验都在**服务端**执行，因为服务端跑的就是这份实现；
3. ✅ **搬数据**：`server/import-data.mts` 用同一份导入逻辑灌入旧导出 JSON，导入前三道保险（结构校验 → 自动备份 → 版本迁移）都在；核对条数看「数据与备份」页；
4. ✅ **登录换成真的**：`lib/auth/session.ts` 改为调服务端，口令由 `server/auth.mts` 持有，前端只拿令牌；
5. ✅ **退出条件**：服务端能通过同一套自检口径，前端没有任何一处直接读写存储 —— `npm run check:both`（同一套断言对内存与真实 HTTP 后端各跑一遍、两边都必须 0 失败）就是这条的证据。

## 9. 自检体系

| 命令 | 盯什么 |
| --- | --- |
| `npm run check` | 内容解析、课程与卡片结构（路径 slug、条目、标签）、报价数据与公式、服务层全流程（增删改查、课时/金额不变式、冲突边界、迁移链）、咨询判定、报价配置前后台一致性、接口契约与文档一致性、前端登录模块（口令不出现在前端源码里、没有后端就明确拒绝登录）（**700+ 项断言**（数量会随功能增长，以命令输出为准）；跑在**内存存储**上，因此不需要服务端） |
| `npm run check:both` | **同一套 `check.mts` 对内存与真实 HTTP 后端各跑一遍**，两边都必须 0 失败。这是「换后端没有偷偷改口径」唯一的证据：第一次跑就抓到四处**静默**差异（同步方法经代理变成 Promise 导致 `hasBackup()` 恒真、空库起步与"首次自动灌示例数据"对不上、老库升级那几段实际写进了浏览器存储） |
| `npm run check:auth` | 起临时后端，用真实 HTTP 验安全边界：未登录的 `/api/call` 与各 REST 接口都必须 401、错口令被拒、令牌能读能写、**操作人来自会话**、退出后令牌立刻作废、伪造令牌 401、`/health` 公开但只回最少信息 |
| `npm run accept` | 逐页验收：**自己起临时后端**，对后台各页面做真实读写（当前 56/56，以命令输出为准）。它本身只是一层运行器，真正的检查在 `accept-check.mts`；后者留着"没指向服务端就直接退出"的闸，否则会安静地测内存伪后端并打印一份假证据 |
| `npm run drill:restore` | 恢复演练：备份 → **先验备份文件本身**（能打开、数据就是刚写的那份）→ 删库（连 -wal/-shm）→ **只靠备份文件恢复** → 重启核对条数与金额一致。没演练过的备份不算备份 |
| `npm run check:404` | 404 产物：分流、标题、样式、未残留默认文案 |
| `npm run check:links` | 产物里的全部站内链接是否都有目标文件 |
| `npm run holidays:fetch` | 节假日表：抓两个公开来源、**逐日比对一致才写** `data/holidays/<年>.json`（`--dry-run` 只校验不写）。不带参数是今年与明年；**"某年还没公布"不算失败**（退出码 0），真失败（对不上 / 连不上 / 写不进去）才非 0 —— 这样"看退出码"的自动化不会每年 10 月报一次假警 |
| `npm run lint` / `npm run typecheck` | 常规质量门 |

需要起服务端的四个命令（`check:both`、`check:auth`、`accept`、`drill:restore`）都共用 `scripts/temp-server.mts`：它起一个**临时库**的服务端、核验 `/health` 报的库名确实是本次这个进程（防"应答的是上一轮残留的旧进程"）、跑完杀**整个进程组**、收尾再确认端口空出来。CI（`.github/workflows/deploy-pages.yml`）只跑 `npm ci` → `lint` → `sync-content` → `typecheck` → `check` → `build` → `check:404` → `check:links`（然后部署到 GitHub Pages）；**上面那四个要起服务端的门禁跑不了 CI，是本机门禁**，改后端相关代码后要手动跑。

**写自检的原则**：只把「框架与口径」写死（栏目名、班型名、不变式），**不写死数量**（卡片数、教师数、方法数会变；写死会让「改内容」和「自检通过」互相打架）。另外，曾经出现过几条**永远为真**的断言（`a === a`、用 `||` 兜底导致恒真、子串匹配让 `lessons.list` 匹配到 `lessons.listByDate`）—— 新增断言时要确认它**会失败**。

## 10. 已知边界与技术债

诚实清单（都是当前阶段的已知限制，不是「以后再说」的托词）：

- **后台数据在服务端数据库**（`server/data/nexgenedu.db`，不进 git）—— 不在浏览器里，换浏览器、清缓存都不会丢；跨机器搬运用导入导出，日常靠**每天自动备份**（保留 90 份）；
- **线上后台连不上后端**：宣传站是静态导出，线上那份产物没有后端地址，因此后台**登录不了**，界面会显示「后台需要本机后端」。要在线上用后台，得先把服务端放到一台能访问的机器上（机构目前决定不做公网部署）；
- **报价仍是双源**：后台配置（在服务端库里）与站点内容（构建期文件）各自一份，靠「导出 → 替换」对齐；
- ~~假登录不是安全机制~~ ✅ **已解决**：登录改为服务端会话（口令在 `server/auth.mts`，前端只拿令牌，未登录接口一律 401）；
- ~~网站内容还没进库~~ ✅ **已解决**（v15 + §5.1）：教师资料、课程卡片、课程正文与报价都能进库并在后台改，
  网站构站时以后端为准、连不上就整体回落模版；
- **页面标题仍是模版**：首页 / 关于 / 联系我们 / 特色课程这些页的标题与文案还在 `data/site/*.md`，
  只有课程页与教师页的标题随内容进了库；也就是说"以后端为准"目前覆盖的是教师、课程、课程正文与报价四块；
- **页面渲染未人工确认**：接口层面有逐页验收（`npm run accept` 56/56），但「页面上真的显示对了吗」还没有人肉眼逐页看过一遍；
- ~~无并发控制~~ ✅ **已分层解决**：同一**条**记录的并发编辑有乐观锁（记录带 `version`，冲突回 409）；
  同一个**库文件**只允许一个后端进程（启动时的单写者锁，第二个进程拒绝启动）；
  跨记录的事务性仍只有「一次整份落盘」这一层 —— 要更强的原子性得换 Postgres（见后端开发方案 §7.2）；
- ~~账号与角色~~ ✅ **已解决**：多账号 + 角色已落地（服务端按方法拦、越权 403、界面按角色隐藏入口），
  **行级范围也已落地**（Phase B：普通教师按账号里的 `teacherId` 只看自己的课与自己学生的课时余额，
  金额字段被剥掉，老 REST 接口对教师整条关闭；口径见 [后台API约定 §三](./后台API约定.md)）；
  **同一条记录的并发编辑有乐观锁保护**（记录带 `version`，冲突回 409），跨记录的事务性没有；
- **每个库只允许一个后端进程**（启动时的单写者锁）：两个进程同时写一份快照会静默丢数据，
  因此第二个进程会被拒绝启动 —— 换成 Postgres（或同等级数据库服务）之后这条才自然消失；
- **快照式存储，没有按行查询**：整库一份 JSON 存在 `kv` 表里，这是「口径只有一份」换来的取舍；数据量或并发真成问题时再逐表迁到 SQL（接口形状不变，页面不动）；
- **操作日志还不是防篡改审计表**：日志已经落在服务端、操作人来自会话（前端说了不算），但接口里仍有 `logs.clear`，登录者可以清空它；
- **后端默认只绑本机**：局域网访问不到（`NEXGENEDU_HOST` 可改，但那是有意识的决定）；
- **后端重启需要重新登录**：会话在服务端内存里，刻意不落盘；
- **教师与课程是部分关联**：教师少，加教师时会按科目自动出现在课程页，但仍有课程没有对应教师；
- **学生「可上课时间」记录了但排课未使用**；咨询里的可上课时间也还没有带进学生档案；
- **教师推荐规则很朴素**（当前取本周课时最少者）；
- **「每两周一次」是固定间隔**，不处理单双周调课；
- **通知/短信/微信不存在**：待跟进只生成话术草稿，人来发；
- **图片未优化**（`images.unoptimized`），也没有真实截图。
