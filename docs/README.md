# 文档索引

这个目录放**系统文档**（怎么写、怎么用、怎么接手）。内容源在 `data/site/`，代码结构与「谁负责哪一块」见 [技术架构](./技术架构.md)。

**当前形态一句话**：宣传站是纯静态站（部署在 GitHub Pages）；教务后台已经接上**本机真实后端**
（Node + SQLite + 服务端会话认证 + 每天自动备份），只在这台电脑上用 —— 线上那份后台连不上后端，
页面会提示「后台需要本机后端」。

## 写文档时的约定

1. **简体中文**，句子写完整；每条规则都要能回答「为什么」，而不只是「怎么做」。
2. **口径与阈值必须能从代码核对**（例如请假 24 小时、教室利用率按上课时间 14 小时/天、教师分成 40% + 每人 10%）：写之前去 `lib/backend/*` 或内容文件里确认一遍，不确定就写「以页面提示为准」。
3. **不要把数量写死**（卡片数、教师数、接口数会变）：需要引用时写「当前 N 个」并说明在哪儿看。
4. **有边界的要说清楚**：例如「单用户：**同一条记录**的并发编辑有乐观锁保护，**跨记录 / 跨进程**的并发仍不在范围内」「后端只绑本机 `127.0.0.1`」「后端重启要重新登录」「线上那份后台连不上后端」这类前提，每个相关章节都要提一次，别只在开头说一遍。**已经解决掉的边界必须把旧说法改掉**：接上服务端之后，凡是指向「浏览器本地存储」的旧说法都成了假话，留着比没有更糟（员工会按错误的前提做事）。这类旧句子不要当例子照抄 —— `npm run check` 会扫描文档里有没有残留的旧说法，引用了也算残留；乐观锁的口径以 [后台API约定 § 6.6](./后台API约定.md#66-乐观锁同一条记录的并发编辑expectedversionv17-起) 为准，其余边界以 [后端开发方案 § 7](./后端开发方案.md) 的边界表为准。
5. **命令与现状同步**：`package.json` 里新增 / 改名命令后，根 [README](../README.md) 的「可用命令」表与这份索引要一起改；**CI 不跑的命令**（要起后端的那几条）要在文档里写明它是「本机门禁」，否则没人会跑。
6. **改了行为就改文档**：`npm run check` 会检查 README 与这份索引里链接的文档是否都存在、核心文档是否都被索引、两份索引有没有说明当前边界、同一份文档里的锚点链接是否指得到标题，还会检查 `docs/后台API约定.md` 是否提到了每一个接口方法 —— 文档漏掉接口时自检会红。
